# Upstream-facing changes

Every change Office Unbound makes to how an upstream application looks or behaves, with the supported hook it uses. Vendor code is not
modified. Each app has its own section; keep them separate.

`opencloud_files`), delivered through `cfg.volume_files`; `blueprints/catalog/components/files.yaml` `config_revision` 3 brings them to

Not possible by configuration (evidence: the deployed web build, `js/chunks/*.mjs` of officeunbound8):
- **Owner and Sharing columns.** The personal-space file table has Name, Status (share and link indicators), Size, Tags, Modified,
  Actions; the column set is fixed per view. Sharing status is visible through the Status icons; owner appears only in the share views.
- **64 px app rail.** OpenCloud Web's extension points (`app.runtime.header.*`, `app.files.*`) have no slot beside the whole layout, and the
  script hook does not know which apps a deployment has (Meet and Calls must be hidden when not deployed, never greyed out). A rail needs
  the list of deployed apps from the portal (proposal: a small `shell.json` from the portal, CORS for the suite's own names, rendered by
  `opencloud-home.js` into a fixed 64 px `nav aria-label="Apps"` with the layout shifted by CSS).
- **`/` key hint in the search field.** OpenCloud already focuses the search on `/` and `S` (web-app-search); a visual hint is not added
  because the location chip ("All files") and the search button occupy the field's right end.
- **Recent / Available offline** entries: OpenCloud Web has no such views.

## Element

Element Web 1.12.35 (`blueprints/build/collab/element-web`, the release tarball, unmodified). `config.json` is generated by
`ics/ics/deploy/configure.py` `element_config`; Office Unbound's own files are written next to it in the chat `front` volume
(`brand.element_files`) and served by the chat front under `/ou/` (`templates/chat/front.conf`). `blueprints/catalog/components/chat.yaml`
`config_revision` 2 brings them to running deployments.

| Change | Hook (supported mechanism) | Source |
|---|---|---|
| Suite colours (light + dark) as the default theme | `setting_defaults.custom_themes` (`colors`, `compound`), `default_theme`, `use_system_theme: false` | `brand.element_themes` |
| Suite font stacks: `"Plex Sans", Inter, ...` / `"Plex Mono", "Fira Code", ...` (Inter and Fira Code are bundled by Element) | custom theme `fonts.general` / `fonts.monospace` | `brand.element_fonts` |
| Home page (no conversation open): product name, three plain actions (new direct message `#/dm`, new room `#/new`, browse rooms `#/directory`), a plain-language paragraph on encryption and the recovery key, link back to the portal; replaces "Welcome <name>" with three large accent cards | `embedded_pages.home_url` -> `https://<chat>/ou/home.html` (Element fetches and sanitises it: no classes, styles or images survive) | `brand.element_home_html` |
| Office Unbound mark on the sign-in consent page (MAS shows the client's logo) | `oidc_metadata.logo_uri` -> `https://<chat>/ou/ou-mark.svg` (must share the client's origin, else Element drops it). Takes effect when Element registers its OAuth client again (new browser profile or cleared site data) | `configure.element_config` |

| Navy backdrop, mark and portal link on the auth pages (earlier) | `branding.welcome_background_url`, `auth_header_logo_url`, `auth_footer_links` | `brand.element_branding` |

Upstream defect found (Element 1.12.35 in Chromium): a custom theme with `fonts.faces` makes Element insert
`<style title="custom-theme-font-faces">` before `<style title="custom-theme-compound">`, and the compound sheet then has no effect: every
compound override is lost (the primary buttons fall back to Compound's near-black). Reproduced on officeunbound8 with the config served to
the browser only (2026-11-27): without `faces` the overrides apply; with `faces`, an untitled copy of the same compound rules applies while
the titled original does not, which fits titled sheets of a different set being treated as alternate style sheets. Office Unbound therefore ships no `faces`; IBM Plex shows only where it is installed, Element's bundled
Inter otherwise.

Not changed: end-to-end encryption, cross-signing, device verification and recovery-key flows (no configuration key touches them;
`ics/tests/test_concept_files_chat.py` asserts it). Their copy was reviewed on the live identity gate ("Confirm your digital identity",
"Use another device", "Use recovery key", "Can't confirm?"): clear enough; Element has a custom-strings mechanism
(`custom_translations_url`) if the owner wants rewording later.

Not possible by configuration: Teams/Channels/Direct messages as named groups in one column (Element's room list groups by its own
sections and filters; spaces stay in the space bar), the channel header tabs Posts/Files/Notes, the thread pane layout, the suite's 64 px
rail (Element has no slot for it; in the portal, chat already opens inside the portal's own frame).

### Concept alignment 2026-11-26 (calendar grid, primary action)

**Calendar grid (stylesheet, row 3).** The calendar paints its cells, date headers and appointments with inline colours from the calendar's
colour scheme (`CalendarDaysView`, `CalendarBoxView`, `AppointmentDaysView`), and upstream dark mode darkens the light cells with
`filter: invert(.85) hue-rotate(180deg)` (`client/resources/css/darkmode.css`). The skin overrides those colours with `!important` and drops
the filter, so the grid uses the suite's surface, canvas and line tokens in both themes: neutral date headers with today in the accent, a
quieter half-hour rule, appointments as a tint of their calendar's colour with a solid bar of it, the current-time line in the accent.
Only colours, borders as colours, inset shadows and background images change; no measured geometry (test enforced).
Upgrade notes: re-check, in a new upstream version, (a) that working-hours cells still carry the scheme's fixed `stripworking` colour
`#ffffff` inline (the skin's `[style*="#ffffff" i]` matcher; `ColorSchemes.js`), (b) the class names `k-line-N`, `k-day-N`, `k-today`,
`k-html-header-background`, `k-appointment-box`, `k-calendar-timestrip-indicator-*`, `grommunio-calendar-boxview`, (c) the dark-mode filter
rule being neutralised, (d) that the half-hour rule is still every even `k-line-N` at the default 30-minute zoom (other zoom levels keep a
uniform line colour). The tests read the upstream 5.2 source when it is present and fail on (a), (c) and the indicator.
Rollback: revert `grommunio.css`; the skin is re-rendered and rolled out with the brand digest (in place, `deployment.change`).

**Primary action (plugin, row 4, package 5.2-ou7).** `navigation.north` components are upstream's supported way to put a component at
the top of the side column (the calendar's date picker uses it). The plugin adds one ExtJS button per item-creating context ("New message",
"New event", "New contact", "New task", "New note"), each tied to its context through `navigationContext` (upstream shows it only while
that context is active) and calling the upstream action the toolbar's New menu calls (`Grommunio.<context>.Actions.openCreate…Content`).
ExtJS sizes it (`height: 36`, `margins`), and the plugin moves its buttons in front of the other north components (the date picker) with
`Container#insert` before the panel renders, so ExtJS lays everything out itself. The stylesheet paints it (accent, white 600 text) and,
only while it exists (`:has(.ou-primary-new)`), turns the toolbar's New split button from copper to the bar navy: the split button stays,
because its menu holds every item type (meeting request, distribution list, …). Labels are English (`_()` with strings upstream does not
translate). Upgrade notes: re-check the insertion point name, `navigationContext` handling in `NavigationPanel.js`, and the five action
names. Rollback: package 5.2-ou6 (the skin degrades by itself: without the button the toolbar New stays copper).

### Assessed and not done (no supported mechanism)

- **48 px top bar.** The main tab bar is 36 px by constructor constants (`MainViewport.createTopbarContainer`: `height: 36,
  boxMinHeight: 36, boxMaxHeight: 36`, toolbar 54 px). No setting or insertion point changes it; CSS would desynchronise ExtJS's own layout
  (forbidden), and a plugin resizing the viewport at runtime would be a geometry override in all but name. Kept at 36 px with the suite's
  navy, the Dashboard pill and the app tabs (Mail, Calendar, Contacts, Tasks, Notes) as the bar's "app name" part.
- **64 px app rail.** The viewport is a border layout whose west region is the navigation panel; Ext 3's border layout allows one item per
  region and grommunio-web exposes no viewport-level insertion point (only `main.content.tabpanel`, `main.maintabbar.*`, `main.toolbar.*`,
  `navigation.*`). A rail would need a source patch to `MainViewport.js`. Closest consistent alternative in place: the app tabs in the bar
  (the rail's Mail/Calendar/Contacts items) plus the Dashboard button to the portal, whose own rail reaches Files, Docs and Chat.
- **Global search in the bar.** grommunio-web's search is per list (the field above each list, styled as the suite's field). No hook places
  a field in the tab bar that drives it.
- **Mail list rows with initials and preview text.** The list request skips the body (`MailGrid#viewConfigGetRowClass` renders only the
  subject in compact rows), so there is no preview text to show without a server change; the only column hook,
  `context.mail.griddefaultcolumn`, appends columns after the flag column, so an initials column would sit at the far right.
- **Selected-view marker in the toolbar.** Day/Work week/Week/Month/List buttons carry no pressed class (2026-11-25 finding, unchanged).
