# ADR-0013 MSP provisioning API (`/api/msp/v1`)
Status: Accepted (design) — Implemented (2026-11-15), see `docs/status/msp-api-results.md`. Roadmap P4.3. Builds on ADR-0002 (security model), 0006 (per-customer isolation), 0009 (deployment engine), the credential vault (`docs/status/credential-vault.md`) and the user lifecycle (`docs/status/user-lifecycle-results.md`).

## Context
MSP systems (clientst0r and others) must be able to create customers, plan deployments, manage customer users, read status and metering, and be told when things happen — without a human clicking through the operator console, and without weakening the guarantees of ADR-0002: every mutation is a typed action → plan → approval by risk → single-use durable job → hash-chained audit.

## Decisions
1. **A separate machine-to-machine surface**, `/api/msp/v1/*`, mounted in the same ICS process but sharing nothing with the console API's auth (cookie session + CSRF + TOTP). The console API keeps working unchanged; an MSP API credential is useless on `/api/v1` and vice versa.
2. **Every mutation creates a plan.** The API has no "do it now" verb. Responses are `202 Accepted` with the plan id, risk, `approvals_required` and, when the customer's policy requires it, the pending customer approval. Previews (deployment plan, change, destroy) are dry runs that write nothing. Plans created through the API are ordinary plans: they show up in the console, need the same approvers, and are bound by the same `params_hash`.
3. **Integrations are per-integration API clients**, never shared users. A client = `client_id` (`mspc_` + 16 hex) + a 256-bit secret (`mspk_…`), a permission set, a customer scope, a rate limit and an optional mTLS binding. Each client is backed by a **disabled, never-enrolled service user** (`msp-<id>`, role operator, `operator_customers` mirroring its scope) so plans can record `requested_by`, existing customer scoping (`tscope`) applies unchanged, and the identity can never hold a console session.
4. **Request authentication = HMAC-SHA256 request signing.** `X-MSP-Client`, `X-MSP-Timestamp` (±120 s), `X-MSP-Nonce` (single use, stored in Postgres so it survives restarts and multiple workers), `X-MSP-Signature = v1=hex(HMAC(secret, "OU-MSP1\nMETHOD\nTARGET\nTS\nNONCE\nsha256(body)"))`. The target includes the query string, so no part of the request can be altered. The nonce is consumed (and committed) only after the signature verified, and stays consumed even if the request is then rate limited or refused, so a captured request cannot be replayed later. Same pattern as rem0te's integration requests (120 s skew + persisted nonce). Optional mTLS: the TLS proxy forwards the verified certificate fingerprint (`X-Client-Cert-SHA256`, which it always overwrites) together with a shared secret in `X-OU-Proxy-Auth` (secret file named by `ICS_MSP_PROXY_AUTH_FILE`; without it a certificate-bound client can never authenticate). The peer address is not used: behind the proxy uvicorn rewrites it to the forwarded client address (review 6 L5). nginx: `proxy_set_header X-Client-Cert-SHA256 $ssl_client_fingerprint; proxy_set_header X-OU-Proxy-Auth <secret>;` (the fingerprint is SHA-1 in nginx by default; configure the proxy to forward the SHA-256 of the DER certificate). HMAC (not bearer tokens) means the secret never crosses the wire and every byte of the request is covered.
5. **Keys are created by an approved plan, shown once, vault-held, rotatable, revocable.** `msp.client.create | set_permissions | rotate | revoke` (and `msp.stack.link`) are admin-only, high-risk (two human approvers) plan actions. The executor generates the secret, stores it encrypted with the ICS vault (AES-256-GCM, AAD = client row id + version), and wraps a copy for the plan's requester, who reveals it once through the console (`POST /api/v1/msp/clients/{plan_id}/reveal`, 24 h, wiped on reveal — the same pattern as identity enrollment tokens). The secret never appears in plan params, audit details, job results or logs. Rotation keeps the previous key valid for a chosen grace period (0–7 days; responses flag `X-MSP-Key-Status`). An API client cannot create, change or revoke API clients.
6. **Permission sets**: `view` (reads, webhooks, event feed), `plan` (previews, submitting plans, one-time enrollment tokens of its own plans), `approve`, `execute`. Default `{view, plan}`. `approve` and `execute` can only be granted through `msp.client.create/set_permissions` with an explicit `acknowledge_elevated`, i.e. by a plan two humans approved. Meaning:
   * **Integration plans never auto-approve.** The ICS auto-approves *low-risk* plans for console operators; for an API client `create_plan(..., msp_auto=…)` replaces that rule. Without `execute`, even a low-risk plan waits for a human.
   * **`execute`** lets a low-risk plan of an **MSP-owned** customer (`customers.msp_owned`) with no extra approvals required and no customer-approval gate run without a human decision — the "explicit, separately approved policy" for auto-approval on MSP-owned infrastructure. Customer-owned infrastructure is never automatic.
   * **`approve`** lets the client approve plans it did **not** request (`decide_plan` still refuses self-approval and provenance conflicts), only for MSP-owned customers and only for non-high-risk plans. High-risk plans always need human approvers.
   An integration can therefore never approve its own plans, and cannot approve anything on customer-owned infrastructure.
7. **Customer scoping reuses ADR-0006's `operator_customers`.** Out-of-scope customers, deployments, plans, jobs and events answer `404` (never `403`) so existence is not disclosed. Customer creation needs an all-customers client. A scoped client may only deploy onto endpoints owned by customers in its scope. Deployments and identity stacks are mapped to customers by `customers.slug` (the deployment engine's `customer_id`) and `idm_stacks.customer_id` (linked by the `msp.stack.link` plan); `tscope.customer_of_params` now resolves those, so deployment/identity plans carry a `customer_id` and the customer policy engine (customer approval, extra approvals, monitoring-only) applies to them too.
8. **Idempotency is mandatory on mutations.** `Idempotency-Key` (8–128 chars) is required on every `POST/PATCH/DELETE`. The key row is inserted **in the same database transaction** as the plan, so "plan exists" and "response stored" commit atomically; a concurrent duplicate blocks on the unique index and then replays. Stored: `(client, key) → request hash (method, target, body hash), status, response` (response encrypted with the vault — it may contain a one-time secret). Same key + same request → the original response, `Idempotent-Replay: true`. Same key + different request → `409 idempotency_key_reused`. 24 h retention. Failed requests are not stored. This makes client retries after lost responses safe (the reference client reuses the key on every retry).
9. **Webhooks**: signed, retried, at-least-once, with stable event ids. Events are captured from the hash-chained audit stream inside the producing transaction (`audit.append` hook → transactional outbox `msp_events` → `msp_deliveries`), so an event exists iff the state change committed. Types: `plan.approved`, `plan.rejected`, `job.completed`, `job.failed`, `incident.opened`, `incident.recovered`. Delivery runs on its own worker thread; retries at 5 s, 30 s, 2 min, 10 min, 1 h, 6 h, 12 h, then dead-lettered (visible per webhook). Signature `X-MSP-Signature: t=<unix>,v1=hex(HMAC(webhook secret, "<t>.<raw body>"))`. URLs must be https and pass the same SSRF guard as endpoints. A subscription only receives events of customers in its client's scope. `GET /events?after_seq=` is the polling/catch-up equivalent.
10. **Rate limits** per client (token bucket, default 120/min, `429` + `Retry-After`), plus a per-address cap on failed authentications (30/min → `429`). In-process state: correct for the single-process ICS; a multi-instance ICS would move the buckets to the database.
11. **Audit.** Every authenticated call appends `msp.request` (client id, method, target, route, status, request id, idempotency key, customer/plan/deployment ids, replay flag) to the hash-chained log as actor `msp:<client_id>`; every failed authentication appends `msp.auth_failed` (reason, claimed id, address). Key lifecycle events are audited by the plan executors. Secrets are never recorded.
12. **Metering has precise definitions** (`docs/api/msp-v1.yaml` and `GET /customers/{id}/usage` → `definitions`): users (active/disabled/deleted), mailboxes (active/disabled holders of the entitlement group; retained = deleted users who held it), provisioned VM resources (desired state of deployment VMs present/changing: count, vCPUs, memory MiB, all virtual disks GiB), observed VM resources (newest inventory snapshot, matched by vmid; boot disk only), mailbox storage = `null` (not measurable yet). Nothing is estimated.
13. **Versioning.** The contract is `docs/api/msp-v1.yaml` (OpenAPI 3.1, checked in; `docs/api/msp-v1-reference.md` is generated from it). Within `v1` only additive changes: new endpoints, new optional request fields, new response fields, new enum values in responses; clients must ignore unknown fields. A breaking change ships as `/api/msp/v2` alongside `v1`. Deprecations are announced with `Deprecation: true`, `Sunset: <date>` and `Link: <successor>; rel="successor-version"` at least 180 days before removal (`gateway.DEPRECATIONS`). Every response carries `X-MSP-API-Version`. The test-suite validates live responses against the spec and checks that routes and spec stay identical.

## Consequences
* A compromised integration can read what it is scoped to and *propose* changes; it cannot execute anything a human has not approved (except the narrow, separately approved low-risk/MSP-owned case) and cannot widen its own permissions or scope.
* Customer-scoped keys limit the blast radius to one customer; the console shows every API client (`GET /api/v1/msp/clients`) without any key material.
* New tables (migration `0011b`): `msp_clients`, `msp_client_customers`, `msp_client_reveals`, `msp_nonces`, `msp_idempotency`, `msp_webhooks`, `msp_events`, `msp_deliveries`; `customers.slug/external_ref`, `idm_stacks.customer_id`.
* Not in v1 (explicit): console UI for API clients (the plan actions and listing endpoint exist), per-endpoint permission overrides, outbound mTLS to webhook consumers, rejecting plans from the API, mailbox usage metering.


## Amendments (security review 6, 2026-11-16)

* **Webhook targets (M2).** `https` only; the name is resolved at creation AND again at every delivery, every address must be global unicast (no loopback, private, link-local/metadata, CGNAT, ULA, multicast, reserved). Exceptions only through the operator allow-list `ICS_MSP_WEBHOOK_ALLOW` (comma-separated hostnames or CIDRs). The connection goes to the address that was checked (TLS name/SNI and `Host` stay the original name), redirects are never followed, and the API reports only `delivered`/`pending`/`dead` (`last_status` is always null, `last_error` is `delivery failed` or null). Creating, deleting and rotating webhooks needs the `plan` permission.
* **Separation of duties (M1).** A human who requested a client, requested or revealed any of its secrets, or is in its principal's creation chain cannot approve plans submitted through that client (`plan.provenance_rejected`). `msp_client_reveals.revealed_by` records the revealer.
* **Customer slugs (M3).** Existing customers get an id-derived slug (`c-<12 hex>`); nothing is bound to a deployment by name. Deployments are bound only explicitly: `customer.create`/`customer.update` with a `slug` equal to the `customer_id` of existing deployments is refused unless `adopt_existing_deployments=true` (high risk, two approvers, audited with the adopted deployments). Derived slugs skip names that would capture a deployment.
