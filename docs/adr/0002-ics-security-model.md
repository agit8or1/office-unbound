# ADR-0002 ICS security model
Status: Accepted (2026-11-15)
1. Operators: local ICS accounts (argon2id + mandatory TOTP), server-side sessions, CSRF protection. Independent of any tenant IdP → doubles as break-glass. Roles: viewer, operator, approver, admin. Requester can never approve own action.
2. Infra credentials: separate identities per purpose. Inventory = privilege-separated Proxmox token with PVEAuditor (read-only). Mutations = a second token scoped to an approved pool/storage/bridge only. Never root@pam, never privsep=0.
3. TLS: always verified, against a CA bundle or an operator-supplied SHA-256 fingerprint pinned at registration. No TOFU, no verify=False anywhere (rejects Depl0y pattern).
4. Secrets: AES-256-GCM encrypted in DB; key in a separate root-owned file readable only by the ICS service user; decryption failure = hard error (no plaintext fallback). Secrets never in logs, audit details, API responses or LLM prompts.
5. Actions: closed catalog of typed actions with validated parameters (no free-form command, image, mount, script fields). Flow: plan → approve (risk-tiered; high risk = 2 approvers) → single-use job → execution → verification. Adopted from rem0te design.
6. Audit: append-only, SHA-256 hash-chained (port of rem0te audit/chain.ts), no request bodies containing secrets; DB role for the app has no UPDATE/DELETE on audit table.
7. No SSH-with-sudo, termproxy, guest-agent exec, or Docker socket exposed via ICS APIs.

## Addendum 2026-11-15: lab-only exception for the ICS-driven SSH guest bootstrap (and the production replacement)
Context: the first real deployment (docs/status/first-real-deployment.md) bootstrapped a stock cloud-image template by logging into the fresh VM over SSH with a fixed-script client in the ICS worker. The independent review (docs/status/review-ssh-bootstrap-2026-11-15.md) found that this is a root-exec primitive in the worker (rule 7 forbids SSH-with-sudo exposed *through ICS APIs*; this is not exposed through an API, but it is the same capability one hop away) and that its failure modes were fail-open.
Decision:
1. **Production: no inbound SSH to guests, ever, and no ICS-side SSH/exec client.** Guests are created from the signed golden image (ADR-0008 pipeline) and enroll through an outbound, HMAC-authenticated, single-use, CA-pinned callback with a random per-VM-instance secret delivered through SMBIOS (docs/status/bootstrap-v2.md). `guest/sshboot.py` is deleted when the first customer deployment ships.
2. **Lab-only exception.** The SSH bootstrap stays in the tree behind `ICS_LAB_SSH_BOOTSTRAP=true`, default off, and **refused at startup unless `ICS_ENVIRONMENT=lab`** (`config.Settings` refuses it in `production` however the object is built). It exists only so that a lab can bootstrap a stock template that has no code of ours.
3. **Conditions of the exception (all enforced by tests):** it fails closed (a persistent seal timer/boot check is armed before anything else; every terminal failure seals + stops the guest and clears the first-contact material); the seal is synchronous, verified by the guest's own MAC'd report and an ICS-side port probe, audited, and repeated on resume; all material is random per VM instance, vault-encrypted and deleted after use; no secret is ever on a command line; the guest proves itself before any payload is sent; the worker can only run named, fixed operations (no caller-supplied script).
4. **Expiry:** the exception ends when the production path has been verified on the real cluster (the golden image imported and a deployment bootstrapped end to end); then the lab flag and `sshboot.py` are removed.
