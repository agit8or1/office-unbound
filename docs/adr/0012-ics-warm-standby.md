# ADR-0012: ICS warm standby controller with fenced promotion

Status: implemented-lab-verified (see [ics-standby-results.md](../status/ics-standby-results.md)). Date: 2026-11-15.

## Context
The directive: the ICS must not become a single point of failure; database, secrets, state and configuration must allow the controller to be restored or replaced; document recovery from the start; HA is a later objective. Today there is a passive restore + manual cut-over ([runbook](../runbooks/ics-recovery.md)); RTO is bounded by backup age and a rebuild. Customer stacks do not depend on the ICS at runtime, so what matters is (1) fast, deliberate takeover and (2) **never two controllers driving agents**.

## Decision
A **warm standby**: a second ICS host that continuously replicates the primary's database, holds the same keys (transferred once, explicitly), runs passive, and is promoted by an operator through a fenced procedure.

1. **Replication: PostgreSQL physical streaming**, over TLS (`hostssl`, `sslmode=verify-full` against the ICS CA, scram), dedicated role `replicator` (REPLICATION LOGIN only), pg_hba line for the standby address only, nftables limiting 5432, a *bounded* physical slot (`max_slot_wal_keep_size=2GB`). Physical, not logical, because the ICS state is the whole cluster: the hash-chained audit log must be byte-identical (a logical copy would re-serialise rows and does not carry sequences/DDL/roles), the standby is read-only by construction (hot standby), and there is no per-table publication to forget when a migration adds a table. Cost: same major version, whole-cluster scope, standby cannot be a different PostgreSQL major. Asynchronous: RPO is the replication lag (observed in the lab: well under a second); synchronous replication was rejected because a dead standby would block the primary.
2. **Keys and configuration: explicit, audited, encrypted transfer at setup**, not continuous sync. `ics-standby-prepare-primary.sh` writes an AES-256-GCM bundle (scrypt, 160-bit generated passphrase delivered by a different channel) with vault/audit/signing keys, env files, replicator password and CA; it appends `standby.keys_exported` to the audit log. Keys do not change in normal operation; any key rotation (`rewrap-master`, signing key) is followed by re-running the prepare script. The standby keeps its *own* TLS CA/console certificate (a name-constrained CA cannot be widened).
3. **Passive standby** (`ICS_ROLE=standby`): no worker/monitor/inventory/backup loops, no credential adoption, migrations skipped when the DB is in recovery, every mutating HTTP method refused with 503 + `X-OU-Role: standby` and a standby page with a banner, and signed agent requests refused in code (`epoch.check_active`). `/readyz` reports `role`, `epoch` and a `replication` check (heartbeat age = end-to-end freshness, replay delay, replay backlog).
4. **Fenced promotion, single writer.** The *controller epoch* (`controller_state`, monotonic by trigger, replicated) is stamped into every signed agent request (`req.epoch`, covered by the signature). Agents persist the highest epoch seen and **refuse any lower epoch** (`stale_epoch`; fsynced before execution) and, once any epoch was seen, refuse epoch-less requests. An agent learns a promotion from the first authenticated request of the new controller. Promotion (`ics-promote.sh` / `ics.cli promote`, root, typed confirmation): refuse while the old primary still streams unless it is fenced in its database first; `pg_promote`; in one transaction epoch+1 and audit `controller.promoted` (replay position = data-loss bound); verify the whole audit chain; flip `ICS_ROLE=primary`, restart; announce the epoch to every enrolled agent with one read-only runbook. A resurrected old primary still has the signing key but carries the lower epoch: agents refuse it, its own `call()` sees `stale_epoch`, and it **fences itself** (`controller_state.role='fenced'`, audited; `/readyz` red, it signs nothing). The old primary returns only as a new standby (`bootstrap.sh --standby-of <new primary> --rebuild`), never by un-fencing.
5. **No automatic failover by default.** Auto-promotion on a timeout is the classic split-brain generator (a network partition looks like a dead primary). Promotion is an operator decision. *Designed, disabled, not implemented:* an optional witness mode - a third small host (or the customers' agents themselves) holds a lease; the standby may auto-promote only when it holds the witness lease AND the primary's lease expired AND it can reach a quorum of agents; promotion still goes through the same epoch fence, which bounds the damage of a wrong decision to "agents refuse the loser".

## Compatibility / migration
Alembic `0009a` adds `controller_state` (epoch 1). Agents are upgraded first: they accept requests with or without `epoch` (mark 0 = legacy). The first epoch-stamped request from the upgraded ICS arms the fence on that agent. Rolling back the ICS after agents saw epoch 1 requires keeping the epoch (agents refuse epoch-less requests): roll forward instead.

## Residual risks (stated, not hidden)
- Between a failure and the first request the new primary sends, an agent has not seen the new epoch; a resurrected old primary could still act on *those* agents. The promote command's announce step closes this immediately for reachable agents; the operator must keep the old primary off until announce reported every node.
- Asynchronous replication: commits in the lag window are lost on promotion (reported in the promotion audit event).
- The agent's journal/epoch files are local state; restoring an agent from an old image resets its epoch mark (re-enroll or re-arm).
- Witness/automatic mode is a design only.
