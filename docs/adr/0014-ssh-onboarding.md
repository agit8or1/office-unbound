# ADR-0014 SSH onboarding ("Connect with SSH")
Status: Accepted (2026-11-16). Evidence level: see docs/status/ssh-onboard-results.md (real sshd + faithful fakes; not yet run against a real Proxmox node).

## Context
Owner request: "want ability to specify ssh for connect your infrastructure. it should login, get the overall config. from there you can select which pve it should have access to and the rights. then it can create its own user with those permissions." and: "the onboarding should create its OWN user, permissions, any ssh keys, etc."

ADR-0002 rule 7 says no SSH-with-sudo exposed through ICS APIs, and the 2026-11-15 addendum deletes the ICS-side SSH client for guests. This ADR adds an SSH path to the **Proxmox node** and must not become a root-exec primitive.

## Decision
### Why this is not an arbitrary-shell API
1. **There is no command parameter anywhere.** The API accepts a connection description and a credential; everything that runs is a typed action (`provider.ssh.discover`, `.preview`, `provider.ssh_onboard`, `provider.ssh_offboard`, `provider.ssh.helper`, `provider.ssh.narrow`) with plan, approval by risk (onboard/offboard high = 2 approvers), single-use job and hash-chained audit.
2. **Closed templates.** `ics/sshonboard/templates.py` is the only place a remote command line is built. Each template is a fixed argv; every interpolated value (node, pool, storage, role, user, token, ACL path, privilege, account, comment) is validated against a strict regex first and then rendered with `shlex.join`. Reads are `pvesh get <allowlisted path> --output-format json`; writes are `pveum ...` and a fixed set of `install/mv/rm/useradd/passwd/userdel/visudo/sha256sum/getent/cat` calls on fixed paths. Non-root users run them as `sudo -n --`.
3. **What approvers see is what runs.** The command list in the plan is produced by running the existing `apply_plan` against a dry-run twin of the SSH admin that uses the same builders; the plan hash (`bind_hash`) covers the permission-plan hash, host, port, user, sudo flag, host-key fingerprint, API-certificate fingerprint, the exact command list, rotated tokens and the node identity (key fingerprint, helper hash, sudoers text). The job recomputes everything over the pinned session and refuses on any difference.
4. **No permission-plan duplicate.** Roles, ACL paths, propagate flags, scope modes, risk and enforcement notes come from the existing generator (`providers/proxmox/provisioning.plan_for`, `apply_plan`, `rollback_created`, `verify_token`). SSH only changes the transport: `SshAdmin` is a duck-typed twin of `ProxmoxAdminClient`.
5. **The admin credential is single-purpose and short-lived** (below) and the ICS never keeps an interactive SSH capability afterwards.

### Transport and trust
* Library: **paramiko 3.5.1** (LGPL-2.1, free of charge; pulls bcrypt and PyNaCl, both Apache-2.0), pinned with hashes in `requirements.lock`. The `ssh` binary is never executed; no agent, no key search, no pty, no shell channel, only `exec_command` of a rendered template.
* **Host key: no TOFU.** `POST /ssh-sessions/{id}/hostkey` performs only the SSH handshake and returns the presented key's SHA256 fingerprint plus `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` for the admin to compare on the node's console. Nothing else runs until the admin types the fingerprint back; it is pinned for the whole flow and for the ICS's later helper connections. A different key at any later connection aborts before authentication.
* **API certificate.** Over the pinned session the ICS reads `/etc/pve/local/pveproxy-ssl.pem` (else `pve-ssl.pem`) and fingerprints the leaf; it must equal the certificate the ICS itself sees on the API address (:8006 or the given URL). Mismatch stops. The fingerprint is pinned for all HTTPS use (verification, registration), as ADR-0002 rule 3.
* SSRF guard (`check_destination`) at session creation, host-key fetch and every connect; link-local/metadata addresses are refused.

### Admin credential
Stored through the credential subsystem (envelope encryption, AAD = credential id + provider `pve-ssh` + customer), purpose `temporary_provisioning`, TTL 30 minutes, bound to the creating operator and customer (a plan for another customer or operator is refused), usable only by the four `provider.ssh*` job types. Never returned by any API (the session view says only that it is in the vault), never in params, results or audit, wiped (ciphertext destroyed) when the onboarding/offboarding job ends in success or failure, on cancel, on expiry (reaper) and when the wizard is left. Validation errors never echo input.

### What onboarding creates (all by the ICS itself, nothing re-uses the admin)
1. **PVE API identity**: user `officeunbound@pve` (pve realm: no Linux account, no shell), roles `OfficeUnbound*`, optional pool (default dedicated `officeunbound`), ACLs, privilege-separated tokens (`--privsep 1 --output-format json`); the secret is parsed from the JSON straight into the vault. The token never receives `Permissions.Modify` or `User.Modify`. Verification over HTTPS (pinned certificate) with the new token must show exactly the planned permission set and no scope reach; any extra privilege fails and rolls back what this run created. Existing ICS-managed user: reconcile; existing tokens are rotated (delete + create) and shown to approvers.
2. **Its own SSH identity on the node**: an ed25519 keypair generated by the ICS (private key only in the vault, bound to customer/endpoint, never displayed); on the node a system account `ou-ics` (locked password, home `/var/lib/ou-ics`), `authorized_keys` line `[from="<ICS address>",]restrict,command="sudo -n /usr/local/sbin/ou-pve-helper" ssh-ed25519 ...`, the root-owned helper `/usr/local/sbin/ou-pve-helper`, its config `/etc/office-unbound/ou-pve-helper.json`, and `/etc/sudoers.d/ou-ics` allowing exactly the helper path with no arguments and no wildcards (validated with `visudo -cf` before activation).
3. **The helper accepts only named operations with validated arguments** read from `SSH_ORIGINAL_COMMAND` and runs fixed argv lists without a shell: `self-check`, `discover <kind> [node]` (fixed paths), `cert-read`, `drift` (effective permissions of its own user/tokens), `token-rotate <own token>`, `acl-narrow <path> <own role> <own subject>` (delete only). There is no operation that adds a user, role, privilege or ACL entry, no pveum passthrough, no generic command. Anything else exits 126.
4. **Where**: single-node scope installs the account and key only on the node the admin connected to, which must be the selected node (otherwise the plan is blocked). Whole cluster: installed on the connected node only; `/etc/pve` and the API token are cluster-wide, so one management node suffices. Trade-off stated to the admin: if that node is down the SSH helper is unavailable (the API token keeps working); adding a second node needs the admin credential again.
5. **Verification after creation (inside the job, rolled back on failure)**: installed helper/config/sudoers hashes equal the approved ones; the new key logs in with the pinned host key; `self-check` hashes match; eight probes outside the allowlist (`id`, `sh -c id`, `bash`, `cat /etc/shadow`, traversal, `;`, `pveum ...`, `acl-narrow ... root@pam`) are all refused; token permissions exact.

### Widening needs a human, narrowing does not
The ICS's own identities can read, rotate their own token and narrow their own ACLs. Adding nodes, storages, pools or privileges, or re-installing the helper elsewhere, needs the administrator's credential again (same wizard with `?endpoint=`) or a Mode B package. A compromised ICS therefore cannot grant itself more. The UI says so in one sentence on the Review step.

### Offboarding
`provider.ssh_offboard` (high; needs a fresh admin SSH session, because the helper cannot delete itself): removes ACLs, tokens, the user and the `OfficeUnbound*` roles that the stored `managed` record says the ICS created, the pool only if requested, ICS-created and empty, then the node account, key, helper, config, sudoers; destroys the vault credentials and disables the endpoint. Guests are never touched.

## Consequences
* Two new tables (`ssh_sessions`, `ssh_identities`), new typed actions, one new dependency (paramiko, LGPL-2.1, zero cost).
* ADR-0002 rule 7 remains true for APIs; this ADR is the explicit, bounded exception for node onboarding, with the checks above enforced by tests (`tests/test_ssh_onboard.py`).
* Mode A (HTTPS password/ticket) and Mode B (package) are unchanged and remain the way to widen without SSH.
* Not covered: password authentication is exercised only in code review (the real sshd used in tests runs as an unprivileged user without PAM); a real Proxmox node has not been exercised (owner test checklist in docs/status/ssh-onboard-results.md).
