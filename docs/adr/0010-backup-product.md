# ADR-0010: Backup product (restic + REST server, ICS-managed)

Status: accepted for the lab (2026-11-15); production deployment follows the Proxmox milestone.
Context: roadmap P5.3, owner requirement "backups are not complete until recovery is tested", ADR-0007 (open source, zero cost), ADR-0002 (typed actions, no arbitrary commands).

## 1. Tool choice

| | restic 0.19 | BorgBackup 1.4 | Kopia 0.2x |
|---|---|---|---|
| License | BSD-2-Clause | BSD-3-Clause | Apache-2.0 |
| Encryption | AES-256-CTR + Poly1305-AE, per-repo master key wrapped by user keys (scrypt); several independent passwords/keys (`restic key add`) | AES-256-CTR + HMAC-SHA256 (1.x), keyfile or repokey; key export (`borg key export`) | AES-256-GCM or ChaCha20, password-derived (scrypt) |
| Dedup | content-defined chunking, whole repository, across hosts | CDC, across the repository (one writer at a time) | CDC |
| Backends | local, SFTP, REST server, S3 (any S3-compatible: MinIO, Garage), Azure, GCS, rclone | local, SSH (needs `borg serve` on the target) only | local, SFTP, S3, WebDAV, rclone, own server |
| Append-only / ransomware | REST server `--append-only` (clients cannot delete history) | `borg serve --append-only` (SSH forced command) | server ACLs |
| Restore verification | `check --read-data-subset`, `restore --verify`, `dump`, `mount` | `check --verify-data`, `extract` | `snapshot verify`, `restore` |
| Maturity | 10 years, one static Go binary, stable repo format v2, release checksums | very mature, Python, repo format changes between 1.x/2.0 | younger, faster, more moving parts |

**Decision: restic.** The REST server gives an append-only listener over HTTPS with per-user credentials and needs no shell account on the target (borg needs an SSH account per client); the repository can later move to S3-compatible storage (self-hosted MinIO/Garage) with no change to the helper; independent keys allow an offline recovery key that does not depend on the ICS vault; `check --read-data-subset=N%` is a built-in periodic integrity read. Borg is a close second (better local-disk speed); kopia was rejected for maturity of its key/server model.

Pinned in `blueprints/lab/common/versions.env`: restic 0.19.1 (asset SHA-256 `f4154156...585c`) and rest-server 0.14.0 (`4c9c95bc...2c66`). The release's `SHA256SUMS` lists the same values; the PGP signature of `SHA256SUMS` was **not** verified (the restic signing key is not in a trusted keyring here; the trust anchor is TLS to the release host plus the reviewed pin). The runner refuses to run a restic binary whose SHA-256 differs from its root-owned config.

## 2. Model

* **Policy** (`backup_policies`): per deployment + tier (`files`, `identity`, `groupware`, `ics`): schedule (`every_hours` or `daily_at` UTC), retention (`last/daily/weekly/monthly`, mirrors `restic forget --keep-*`), RPO and RTO targets, repository (`https://host:port/name` of a rest-server + SHA-256 pin of its certificate), verification cadence (repository check every N s reading P % of the data; restore verification every M s), runner node.
* **Actions** (all typed plans, audited): `backup.policy.create` (normal), `backup.policy.update` (normal, **high** when retention shrinks: the next prune deletes history for good), `backup.run`, `backup.verify`, `backup.prune` (low; prune takes the retention **from the policy**, the caller cannot choose one).
* **Execution**: the ICS sends the signed agent request `backup.run {tier}` / `backup.verify {tier, level, [percent], [snapshot]}` / `backup.prune {tier, last, daily, weekly, monthly}`. The agent validates closed shapes, spools them and starts the fixed template unit `ou-rb-backup@<rid>.service` (polkit allows exactly that template); the root helper `ou-backup` re-validates and reads everything environment-specific (source machine, repository, credentials, scratch machine, scripts) from the root-owned `/etc/ou-backup/<tier>.json`. No command line, path, repository or credential can be supplied through the API. Hooks are the existing online tier scripts (`files-backup.sh`, `id-backup.sh`, `gw-backup.sh`, `ics-backup.sh`).
* **Lanes**: `backup.*` jobs run on their own worker lane (job budget 3600 s) so a restore verification never blocks remediation jobs; the scheduler runs in the same thread and creates at most one plan per policy and tick (one in flight per policy+action; failed backups are retried after 15 min, never queued up).
* **Keys**: the restic repository password (256 bit) is generated by the job, stored vault-encrypted with AAD `backup-repo:<policy id>:<hash of repo URL>`, never returned by the API, never in an audit entry or job result (tested). Provisioning it on the node is a host-root step (`ics.cli backup-node-secret | ou-backup --direct provision <tier>`, audited, value never logged) because the agent protocol deliberately carries no secrets. The owner's **offline recovery key** is a second restic key (`ou-backup --direct recovery-key <tier> <file>`), written to a 0600 file once; ICS records only a 16-hex fingerprint (`ics.cli backup-recovery-ack`). Losing the vault key then no longer loses the backups.
* **Append-only**: the runner's REST credential can add but not delete or overwrite; pruning uses a second listener/credential that exists only in the maintenance runner config. In the lab both live on the same runner (limitation, see results).

## 3. Four states (never collapsed into one flag)

`backup_success` (last run succeeded and the snapshot is within RPO; `warning` at 1.5x, `critical` beyond), `replication` (copies confirmed vs `copies_required`; the lab has one repository, so `copies_required: 2` shows `degraded`), `recovery_readiness` (a repository check passed recently AND the recovery key was exported AND a fresh snapshot exists), `verified_restore` (a restore into a scratch machine matched the canary, within its maximum age; RTO measured and compared with the target).

Verification state machine: `pending -> running -> passed | failed | error` (`failed` = ran and the result was bad; `error` = could not run). A restore without a recorded canary can never pass (`judge_canary`).

## 4. Monitoring

Check kind `backup` (aspects `age`, `repo_check`, `restore`, `growth`) is evaluated from recorded runs, so it uses the normal check/incident/alert pipeline (thresholds, flap damping, channels, maintenance windows).

## 5b. Per-customer boundaries (agent AU, 2026-11-15; closes the T20 backup FAIL)

* **Binding**: `backup_policies.customer_id` (migration 0009; NULL = MSP-internal). Plans for a policy carry the policy's customer, so the existing operator scoping applies (404 for foreign and for missing policies alike); the read API filters by scope; at job time the plan's customer must equal the policy's (defence in depth).
* **Namespace**: profile `c-<32 hex>` derived from the customer id. It is the first path segment of the repository URL, the REST user (rest-server `--private-repos`: a user reaches only `/<user>/...`), the runner config directory `/etc/ou-backup/<profile>/` (own credentials and staging directories) and an entry in the agent's `customers` allowlist. Runbook parameters carry the profile (closed shape); the agent and the root helper re-validate it and the helper refuses configs that cross namespaces or share machines with another profile.
* **Keys**: repository password per policy, vault AAD includes the customer id; REST credentials per customer and per listener (append-only vs maintenance). Three independent barriers: REST authorisation, repository encryption key, ICS scoping.
* **Policy classification**: `backup.run`, repository checks and policy management read the customer's stack and write only to the backup repository (not "infrastructure changes": no customer approval, allowed for monitoring-only customers); prune and restore verification stay gated.
* **ICS controller tier**: `tier=ics` has a restore verification (passive restore into a scratch machine, chain + head event + schema + passive + operator login); the hook is parameterised (`OU_ICS_PREFIX/DB/ROLES/DB_OWNER`) so a dev ICS can be protected and verified without touching the production service.

## 5. Consequences / not done

* Production runner topology (runner node per site vs per tier) and S3-backed repositories are defined by the interface (`repo.backend`), only `rest` is implemented.
* Second-copy replication (`restic copy`) is modelled as a state but not implemented.
* ICS controller tier: lab-proven against a DEV ICS only; no run against the production controller yet (deliberately).
* Files-tier online backup is crash-consistent per file (no stop); production needs a filesystem snapshot.
