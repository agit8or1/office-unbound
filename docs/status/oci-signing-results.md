## 1. Review-6 H1 and the runner model (review 7 H-3)

What was wrong: `ou-image-sign record-test <sha> <name> <pass|fail> <log>` was reachable by the build user via `sudo ... ou-image-sign *`, so the party that supplies the image also wrote the "first boot passed" record. My first fix (a runner that signs evidence the caller hands over) was itself self-attestation and is **not what is shipped**.

What is shipped, consuming the interface of `fixes-r7` (`ou-test-attest run <kind> <ref>`, v2 attestations) instead of a parallel runner:

* **`ou-test-attest run image-first-boot <absolute image path below /var/lib/ou-imgbuild/out>`**: the caller names an artifact and nothing else. The runner (user `ou-testrunner`) copies the file (no symlink, regular file), hashes it itself, and runs the FIXED program `/usr/local/lib/ou-testrunner/image-first-boot` on the copy. That program asks a root-owned helper `image-boot-root` (sudoers: `ou-testrunner ALL=(root) NOPASSWD: /usr/local/lib/ou-testrunner/image-boot-root`, **no arguments**, the helper re-validates the request path) to copy the image into `ou-img1`, run `bootproof.sh` (qemu TCG first boot -> guest callback -> HMAC -> enrollment over pinned TLS -> bootstrap secrets wiped), and to judge the `evidence.json` that `bootproof.sh` wrote (`image_sha256` must equal the image that was booted, `enrolled`, `final_state=enrolled`, `secrets_wiped`, `agent_key_matches_report`). Exit 0/1 is the verdict; any infrastructure problem produces **no attestation**. There is no argument, stdin field or file through which a result can be passed in.
* **`ou-image-sign record-test`** takes no argument; stdin is one attestation. It verifies the Ed25519 signature against the root-owned `trust/test-runner.pub`, `v == 2`, `kind == image-first-boot`, and that `at` is newer than any earlier record (an old pass cannot replace a later fail); `sign` re-verifies the stored attestation (a tampered record file is refused).
* **Sudoers (`/etc/sudoers.d/ou-image-sign`) has exactly three exact lines** (`sign`, `record-test`, `pubkey`); no `*`. Arguments are validated inside the program as well.
* **Regression tests** (`ics/tests/test_golden_image.py`): the old 4-argument form is refused; a fabricated `pass` attestation with a garbage signature, one signed with the build user's own key, and a v1 attestation signed with the genuine runner key are all refused and no record is written; fabricated `pass` evidence passed on the runner's stdin is ignored (the fake boot program decides by the image bytes: the verdict was `fail`); a path outside the image directory, a symlink, a wrong kind, an extra argv word and the removed `attest-image` entry point are refused; an older record cannot replace a newer one; a tampered record file is refused at sign time; the sudoers rules have no `*`.
* **Real run (2026-11-16 02:1x UTC):** `sudo -u ou-testrunner ou-test-attest run image-first-boot /var/lib/ou-imgbuild/out/ou-golden-debian-12-20261115.qcow2` -> `ou-img1` booted the image (image sha256 `690d6514c896...`), verdict `image_sha256 ok, enrolled=True final_state=enrolled secrets_wiped=True key_matches=True -> PASS`, attestation run id `89513ce380e4dbf28b2aaa66e4070c70` (log kept in `/var/lib/ou-testrunner/logs/`). `ou-image-sign record-test` accepted it and `ou-image-sign sign` produced `SHA256SUMS` + `SHA256SUMS.sig` for that image (public key pin unchanged: `1756953ac4503f01fd1a08968fefef2e5f6712a542d42a21b634892a60eff1ec`).
* **Still true (not hidden):** the runner and the signer are separate users, but `administrator` still has `NOPASSWD: ALL` on this lab host, so the separation is on paper until that rule is removed (owner). `image-boot-root` trusts `ou-img1` (its qemu, its ICS copy under `/opt/ics-src`) to produce `evidence.json` honestly; that machine is a lab builder, not a hardened test environment. The boot proof is TCG, not Proxmox.

## 2. `ou-oci-sign` (hardened OCI signing)

Files: `blueprints/build/oci/signer/{ou-oci-sign,install-oci-signer.sh,install-oci-runner.sh,oci-publish-sig.py}`, `blueprints/build/oci/testrunner/oci-scan`, client `blueprints/build/oci/oci-sign.sh`.

* **Own user `ou-ocisign`**, home `/var/lib/ou-ocisign` (0700). **One ECDSA P-256 key and one passphrase file per channel** (`key-dev.pem`, `key-staging.pem`, `key-stable.pem`; review 7 "separate keys per channel"). Dev images are signed with the dev key only; hosts pin one channel's public key, so a dev signature does not verify on a staging/stable host (tested, and shown with `skopeo` in section 6). Pins (SPKI sha256): dev `cd28d8bcc53aa2568d28c259b0923bc87f5e1bbd21e09e1bcdf28280aae7ee10`, staging `f2b9292757eb79f714316eace1bb7051661f8f725a667b0929009b2d31aa118d`, stable `8a2405f88e153295422b21a30748fbe441bb04a05f3f4e4f3919b4535c8a7c52`.
* **Sudoers (`/etc/sudoers.d/ou-oci-sign`): exact lines** `ou-oci-sign sign` and `ou-oci-sign pubkey dev|staging|stable`. No wildcard. The signer takes no argument; the request is a tar on stdin and every field is validated inside the program (repo must be under `ou/`, tag, digest, channel).
* **Signature format:** cosign "simple signing" payload (`{"critical":{"identity":{"docker-reference":"<registry>/<repo>"},"image":{"docker-manifest-digest":"sha256:..."},"type":"cosign container image signature"},"optional":{channel, sbom sha256, scan attestation sha256}}`), ECDSA P-256/SHA-256 (ASN.1 DER, base64), stored as a registry attachment (`sha256-<hex>.sig`) by `oci-publish-sig.py`, which holds no trust. Verified by `skopeo`/`podman` with `sigstoreSigned` + `signedIdentity: matchRepository` and the channel's public key.
* **It refuses unless:** (a) the registry (named in the root-owned `trust/registry`, never by the caller) serves a manifest whose bytes hash to the digest, its config and layer blobs exist, and the tag (if it still exists) points to the same digest; (b) the SBOM is a CycloneDX inventory whose `metadata.component.version` is that manifest digest and whose sha256 equals the one inside the scan attestation (bound by hash); (c) the **scan attestation is the runner's** (v2, kind `oci-scan`, Ed25519 by `trust/test-runner.pub`, names this digest, repo and config digest, completed, not older than 14 days); (d) **staging/stable only**: the previous channel was signed here for this digest, the scan has no unwaived critical finding (`critical_unwaived == 0`), and the ICS-signed `release.promote` manifest (`trust/ics-promotion.pub`) is for `<previous>><channel>`, names exactly `oci:<repo>:<tag>` + digest + this scan attestation, has the required distinct approvers (stable: two, requester excluded), is unexpired (<= 24 h lifetime) and is single use.
* **The scan is the runner's, not the caller's:** `ou-test-attest run oci-scan <repo>@sha256:<hex>` (new kind added to the `fixes-r7` runner): it pulls manifest and blobs from the registry named in the root-owned `/etc/office-unbound/oci-registry`, re-hashes every byte, writes an OCI layout in its private work dir and runs the FIXED root-owned `oci-scan` (pinned syft 1.57.1 and osv-scanner 2.7.1 from `blueprints/build/tools.env`, sha256-verified at install). The runner hashes the SBOM and copies the counts into the signed attestation itself. Findings are **recorded, not judged**: `critical_groups` / `critical_unwaived` (CVSS >= 9.0 groups minus a root-owned, reasoned, expiring waiver file `/etc/office-unbound/oci-vuln-waivers.json`, not created yet). The dev channel may carry findings (it is the triage channel); staging/stable refuse them.
* **`release.promote` for images (ICS):** components named `oci-*`, one image per plan, `file = oci:<repo with / as ~>:<tag>`, `sha256` = manifest digest, exactly one evidence entry (the scan attestation hash for that digest); executed by a separate command `ICS_RELEASE_PROMOTE_OCI_CMD` (new setting). Tests in `ics/tests/test_release_promote.py`.
* **Tests (`ics/tests/test_oci_signer.py`, 12):** dev signature verifies only with the dev key; extra argv, extra/missing tar members, bad repo/tag/digest/channel; digest missing, registry lying about bytes, missing layer, moved tag; SBOM of another image / not bound by hash / too thin; attestation forged, failed, stale, for another digest, wrong kind, edited after signing; staging/stable gates (no manifest, dev never signed, forged ICS signature, wrong direction, no approvers, requester among approvers, expired, wrong package set, evidence mismatch, replay, stable needs two approvers, unwaived critical finding); the runner pulls and scans by reference only (an extra argument, a bad reference, fabricated stdin evidence, lying registry are refused/ignored and the runner output is accepted by the signer); waivers count only with a reason and an unexpired date.
* **Installed on this host** (`host-changes.md`): `install-oci-signer.sh`, `install-oci-runner.sh` (replaces `/usr/local/sbin/ou-test-attest` by the branch version, which contains the whole `fixes-r7` runner plus the new kind), `install-image-signer.sh`.

## 4. Jitsi server components (`blueprints/build/oci/jitsi/`): choice and justification

**Chosen: the signed `.debs` of Jitsi's apt repository, with the whole chain pinned, not a Maven source build.** Reasons: jicofo and jvb are Kotlin/Java projects with hundreds of Maven artifacts including Jitsi's own libraries that are published on Jitsi's own Maven repository (not authorized; only Maven Central is); jitsi-meet-web is a webpack bundle that only Jitsi's release process produces. A source build would have meant either unauthorized endpoints or an unverifiable approximation. What is pinned instead (`01-fetch-verify.sh`, all refusals exit 4):

1. Repository key `FFD6 5A0D A2BE BDEB 73D4 4C8B B4D2 D216 F1FD 7806` ("Jitsi <dev@jitsi.org>"): the script fetches it from `download.jitsi.org/jitsi-key.gpg.key` **and** from `keyserver.ubuntu.com` and requires both to carry exactly this fingerprint.
2. `InRelease` verified with VALIDSIG by that key (Release dated 2026-09-14), `Packages.xz` sha256 compared with the signed `InRelease`, every `.deb` sha256 compared with both the signed `Packages` entry and the pin in the script.
3. Content extracted with `dpkg-deb -x` (maintainer scripts never run), into our own minimal images. Prosody comes from the Ubuntu archive (distro-signed), not from Jitsi.

Release set (`jitsi-meet 2.0.11248-1` closure): jicofo `1.0-1205-1`, jitsi-videobridge2 `2.3-318-gbf271b11f-1`, jitsi-meet-web / -web-config / -prosody / -tokens `1.0.9442-1`; hashes in `evidence/jitsi-debs.sha256`. Images (non-root, uids 10080/10090/10100/10110): `jitsi-web` `sha256:5dc54c4a...`, `jitsi-prosody` `sha256:6e778478...` (prosody 0.12.4-1build3; the pure-Lua libraries that noble ships only for Lua 5.1-5.3 are linked into the 5.4 path), `jicofo` `sha256:0263ee9f...`, `jitsi-videobridge` `sha256:02961738...`.

**Telemetry / third-party traffic:** `config.js` is rewritten at build time (`disableThirdPartyRequests: true`, `analytics.disabled: true`, Jitsi's public STUN relay removed; the build prints the remaining uncommented third-party references: none); the videobridge ships `defaults.conf` (no AWS harvester, no STUN mapping harvester, no stats transport) merged under the operator's `jvb.conf`. Jicofo has no analytics handler configured.

**Not verified:** jicofo and jvb were started (jar + JVM + config merge; JVB logged "Starting jitsi-videobridge version 2.3.318") but not run against a deployed prosody with a brewery MUC, so no media was relayed; the nginx upstream names are resolved at start (they must exist on the container network).

## 7. What the scan numbers mean (and the open triage)

The runner records 110-281 OSV advisory ids per image and a maximum CVSS of 9.8 for every image except `office` (8.5). These come overwhelmingly from the Ubuntu base packages (OSV matches by source package and does not know Ubuntu's fix status), exactly as in `collab-images-results.md`. They are **recorded and not triaged**. Consequence by design: **dev signatures exist; staging/stable signing is refused for these digests until the critical groups are triaged** and covered by reasoned, expiring waivers in `/etc/office-unbound/oci-vuln-waivers.json` (or the base is rebuilt). That is the intended gate, not a defect, but it means the images are not promotable today.

## 9. Open items / honest limits

1. **Registry host.** Signatures are bound to the lab registry reference `192.168.186.235:5000/ou/<name>` (`trust/registry`). The catalog still uses the placeholder host `registry.ou.invalid`; with `matchRepository` a production policy needs the real registry host written into the signer's `trust/registry` before production signing and the images re-signed (digests are registry independent).
2. **staging/stable never exercised on the host:** no ICS promotion public key is installed (owner supplies `OU_ICS_PROMOTION_PUB`); covered by unit tests only.
3. `administrator` keeps `NOPASSWD: ALL`; the user separation is on paper until the owner removes it. The lab registry listens on `0.0.0.0:5000` in the builder (zone `oulab`) without authentication (was 127.0.0.1).
4. The previous `ou-image-sign` record for the golden image (typed, v1) is gone in effect: it carries no attestation and `sign` refuses it; the new real run replaced it.
5. The builds are not bit-reproducible (apt layers, build time in the image config).
6. Keycloak 26.8.2: Maven Central (sha256 + sha1) and the GitHub release (sha1) agree, but upstream publishes only sha1 on GitHub; no PGP verification of the Keycloak tarball was done (Maven Central `.asc` exists: follow-up). OpenCloud: release `.sha256` and GitHub's asset digest agree.
7. `pull-test.sh` uses vfs storage and removes it after every pull (a 1.5 GB machine is OOM-killed otherwise).
