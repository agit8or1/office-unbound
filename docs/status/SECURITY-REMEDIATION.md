Locations are written `sha:path:line` (a leading 7-hex sha means "at that commit"; no sha means this file's commit, i.e. `main`).

**How this was produced.** Every row was checked against the code at the stated commit with `git grep`/`git show`: the fix location was found by reading the source, not copied from a remediation table. Regression tests were located by name. Marks in the test column: **[A]** = the test body was read and asserts the fixed behaviour; **[E]** = the test exists by name and file but its body was not read here. **No test suite was run for this document.** Where a remediation table claims something the code contradicts, the cell says **CLAIM NOT VERIFIED** and why.

**ID scheme.** `R1` = ICS review (security-review-ics), `R2` = ICS monitoring review, `R3`..`R7` = security-review-3..7 (R7 rows are the review's *new* findings `H-1`..`L-8`; its verdicts on older rows appear in the "Independent verification" column), `RS` = SSH-bootstrap review, `OA` = owner actions that gate other rows (counted separately). Review-4 and review-5 "Fix verification" tables are folded into the rows they judge.

**Status vocabulary.** *Fixed on main*; *Fixed on branch `<b>@<sha>` (pending merge)*; *Partial*; *Open*; *Accepted risk* (reason + owner sign-off needed); *Owner action*. "Fixed" means the code at the stated commit does what the finding asked for. It does not mean the fix is deployed on the live host (see the notes at the end).

## Reproducing the check

`python3 scripts/security_remediation_check.py` (from the repository root) parses the findings table, confirms every `file:line` exists and is within the file, every `file::test` names a test that is defined in that file, that every status is in the vocabulary, that every row not fixed on main has a remaining-risk entry, and that the summary counts match the table. Refs that are not present in a clone (branch-only commits) are reported as warnings; use `--strict` to make them errors.
