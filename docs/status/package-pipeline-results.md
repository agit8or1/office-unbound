## 2. Pipeline steps: what was executed

1. **Fetch + verify.** Clone of the pinned tag, check `tag^{commit}` equals the pinned SHA (and the tag object SHA for annotated tags), export a deterministic `git archive | xz` orig tarball (checksum recorded in `out/<c>/source.info`). Tag signatures: gromox, libHX and wmime tags are OpenPGP-signed by key `2BDA563E9DDE46AF71CC171DAEB6941A2F9C9944` (tagger Jan Engelhardt); the build checks the signing key id against the pinned fingerprint but **cannot validate the signature** because the public key is not available from an authorized endpoint (finding: the check is an identity pin, not a cryptographic verification). The other five tags are unsigned (SHA pin only). admin-api uses a lightweight tag.
2. **Patch queue** applied by `dpkg-source` (quilt). Patches carry DEP-3 headers.
3. **Licence check** (`lib/licensecheck.py`): SPDX tags + licence files of the source tree, lock-file licences of bundled npm/composer packages, inventory presence. Result PASS for all eight. Real findings that were fixed on the way: `mapi-header-php` was missing from the inventory (added, section 8), the policy lacked deprecated-alias handling (`LGPL-3.0+` of openpgp 6.3.2), Gromox's custom "linking exception" texts are allow-listed explicitly and stay on the lawyer list. Warnings (declared set differs from found set) are recorded in `license-report.json`.
4. **Build** in `ou-pkg1` (Debian 12, fresh clone of `ou-base-bookworm`, zone oulab, PrivateUsers=pick, MemoryMax=3G, JOBS=3). Build dependencies are installed with `apt-get build-dep` from Debian bookworm/-updates/-security and from a builder-internal flat repo of our own earlier packages (ou-libhx-dev etc.); exact installed versions of everything are recorded in `out/<c>/artifacts/build-env.txt` (plus `out/builder-manifest.txt`, sha256 `2d41c71f0d9e3537...`). `SOURCE_DATE_EPOCH` = commit date of the pinned commit; fixed build path `/build/work/<c>/<src>-<ver>`; `LC_ALL=C.UTF-8`, `TZ=UTC`. **The compile step runs in an empty network namespace (`unshare -n`)**: network is only available in the explicit `prefetch` phase (npm ci from `package-lock.json`, composer install from `composer.lock`, pip install `--require-hashes` from `requirements.lock`), which runs after the source package is created and before the network is removed.
5. **SBOM** (`lib/sbom.py`): SPDX 2.3 JSON per binary package = dpkg metadata + pinned upstream commit + patches + runtime `Depends` resolved to the exact installed version + bundled npm/composer/PyPI packages from the lock files (purls). Cross-check with **syft 1.57.1** (pinned, sha256 verified) over the package payload (`*.syft.spdx.json`). Files in `out/<c>/sbom/`.
6. **Vulnerability scan** (`lib/vulnscan.py`): osv-scanner 2.7.1 (pinned, sha256 verified; queries the OSV database, an authorized endpoint) over each SBOM. Results are recorded, they do not fail the build.
7. Lintian is run on every build (`artifacts/lintian.txt`). Remaining error-level tags: none after the fixes; warnings are copyright-format and `link-to-shared-library-in-wrong-package` (Gromox plugins are loaded via the `.so` symlinks, intended).
8. **Signing** is a separate step on the ICS host (`repo.sh index` uses `sudo gpg --homedir /etc/office-unbound/release/gnupg`); the builder never sees the key.
9. **Channels** `dev`, `staging`, `stable` are separate suites with separate pools (`dists/<suite>/{InRelease,Release,Release.gpg}`), generated with `apt-ftparchive`.

## 3. Promotion gate

`repo.sh promote <from> <to> <component> [--approved-by NAME]` copies a component's packages to the next suite only if **every .deb has a recorded passing `install-smoke` test** keyed by the deb's sha256 (`records/tests/<sha256>.json`, written by `repo.sh record-test`), only dev>staging and staging>stable are allowed, and stable additionally requires an approver name (stand-in for the ICS approval record, ADR-0008 step 9). Every promotion is appended to `records/promotions/log.jsonl`. Executed (`out/promotion-demo.log`): promote with no record REFUSED; promote after a recorded `fail` REFUSED; promote to stable without approver REFUSED; after the passing `pkgtest.sh dev` run was recorded all 8 components were promoted dev > staging > stable. The final `pkgtest.sh stable` run (only the stable suite) passed again with the identical result.

## 5. Reproducibility observations

* Bit-identical `.deb`, `.dsc` and tarballs across two consecutive builds in the same builder (same pinned inputs): libhx, wmime, mapi-header-php, grommunio-sync, grommunio-dav, grommunio-web (including the npm build) and admin-api (including its compiled PyPI extensions, after the fix below).
* Gromox: the 73 ELF files (binaries and libraries, `ou-gromox`) and `mapi.so` had identical sha256 across **three** builds. The `.deb` itself changed between runs only because packaging files changed in between (sysusers/tmpfiles/postinst fixes), not the compiled content.
* Found and fixed: (a) composer's random autoloader class suffix made `ou-grommunio-dav` non-reproducible; fixed with `composer config autoloader-suffix OUDav` in the recipe prefetch. (b) `ou-admin-api` differed because mysqlclient and systemd-python are compiled from sdists by pip in random `/tmp/pip-*` directories (paths and build ids end up in the `.so` files); fixed with `-ffile-prefix-map=/tmp=...`, `-g0`, `-Wl,--build-id=none` in the prefetch environment. Wheels with binary payloads (cryptography, cffi, ...) are hash-pinned and identical by construction.
* Techniques that mattered: `SOURCE_DATE_EPOCH` from the pinned commit, fixed build path, `-ffile-prefix-map` (debhelper default), `dh_strip_nondeterminism`, deterministic `git archive | xz -T1`, `dpkg-source` before the prefetch.
* **Not proven**: reproducibility across different builder images/hosts (all runs used the same `ou-pkg1` state, which also changed between the first and later runs: nodejs and python tooling were added; the gromox binaries stayed identical across that change). Debian build dependencies are not pinned to snapshot.debian.org: they are the current bookworm point release (versions recorded per build). A second builder machine rebuilt from scratch would be the real test.
* **Comparison with the source-built lab (`ou-gw1`, read from the host filesystem, nothing run on the machine)**: not byte-identical, as expected (different flags: the lab build is unstripped, no hardening, `make install` from `/usr/src`; e.g. `libexec/gromox/http` 5.2 MB lab vs 0.3 MB stripped here). Meaningful equivalences: our package contains exactly the lab's `gromox*`/`libgx*`/`libgromox*` file set minus the libtool `.la` files (0 files only in ours, the `.la` files only in the lab), and the exported dynamic symbol sets of `libgromox_mapi`, `libgromox_common` and `libgxs_exmdb_provider` hash identically (nm -D).

6. Vulnerability triage (libxml2 Debian CVEs, postal-mime) and a per-package licence scan of the admin-api PyPI wheels and of the npm tree actually shipped (the lock-file scan covers declared licences only).

What changed in the pipeline itself:

* **Signing is no longer reachable from the build user.** `repo/ou-release-sign` (runs as the system user `ou-release` through one sudoers rule) holds the key (passphrase-protected, same fingerprint `5D2750D0...F84C1B`), keeps per-suite ledgers of admitted file hashes, test records and clearsigned promotion records, sets `Date`/`Valid-Until` (14 days) and signs. `repo.sh` can no longer sign or promote anything on its own. `repo.sh resign-all` plus `ou-repo-resign.timer` (shipped, not installed) keep `Valid-Until` alive. `install-signer.sh` is the root-only, idempotent installer. Regression test: `tests/test-pipeline-security.sh` (30 PASS). Section 3 above describes the old advisory gate; the enforced version is this one. Earlier promoted versions now stay in the target pool (a rollback needs them): promotion no longer deletes the previous version.
* **Builder output is hostile** (`lib/artifact-check.py`, used by `build.sh` and `repo.sh publish`): regular files only, `.deb` and `.dsc` parsed with `dpkg-deb`/field checks and matched to the recipe (package names, version `<upstream>-<ou_revision>`).
* **Ephemeral builder:** golden image `ou-pkg-golden`, a fresh clone per compile, destroyed afterwards; prefetch as the unprivileged user `obuild` with `--ignore-scripts`. `ou_revision` is a per-recipe field (`OU_REVISION` in tools.env is only the default).
* **Repo server:** `repo.sh serve` pushes the public tree to the dedicated machine `ou-repo1` (read-only, root-owned tree), not to the builder. `pkgtest.sh` records its own test result for exactly the `name_version` packages it installed; `pkgtest-guest.sh` copies only the suite under test (the full copy per tamper case had grown to 1.4 GB and filled the tester's tmpfs, which first showed up as a MariaDB "No space left on device" failure of the smoke test).
