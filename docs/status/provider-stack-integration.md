# Provider stack integration (INT2): provisioning (L) + credential vault / customers (M)

Branch `provider-stack` = `provisioning-l` + `vault-m` (both on provider branch A). Not merged with main. Evidence: Proxmox simulator only (`tests/test_provider_stack.py`, plus both
original suites); nothing ran against a real cluster.

## Merge
Textual conflicts in `actions.py` (action enum, catalog, executors, `_SAFE_ERRORS`, plan hooks), `main.py`, `worker.py`: resolved as the union (L's `prov_service.tick` and M's
vault/approval tick both run). Migration chain: `0006a -> 0007l -> 0007m -> 0008i` (0007m re-chained after 0007l; 0008i adds `provision_artifacts.customer_id`).

## Integration points
1. **One secret store.** Token secrets captured by Mode A / imported in Mode B reach endpoints only through `endpoint.register/update` (`credentials.attach_endpoint_credential`);
   drift, rotate and reconcile read them with `credentials.endpoint_secret` (L's own `_vault_token` decryption is gone); `provider.token.revoke` calls `release_endpoint_role` (ciphertext
   destroyed). Temporary admin credentials of provider plans are NOT stored in `plans.secret_enc` any more: `create_plan` creates a `temporary_provisioning` credential with
   `id = plan id`, TTL 15 min, envelope encrypted; the plan digest binds `credential:<plan id>`. The job loads it via `get_secret` (audited `credential.use`). Discard
   (`provisioning.actions.scrub_expired_credentials`, called on job end, plan reject/expiry, customer reject and by the reaper) revokes every temporary credential that is expired, whose plan
   was rejected/vanished or whose job finished: ciphertext destroyed. The M expiry/alert tick ignores them (no alert noise).
2. **Plan provider.** `provisioning/customer_plan.py` registers the `proxmox` builder: for `provider.provision.package|apply` the customer approval proposal contains the real design
   (every path/privilege of every role, elevated privileges) and the real Mode B package files (inside the hashed proposal). `POST /api/v1/public/approvals/package` (token in body, same
   link rules) returns them as a zip; the approval page shows a download button. Other actions still use M's stub. Caveat: the proposal is computed offline (needs `pve_major` or the
   endpoint's last probe); the package finally generated by the approved job uses live facts and can differ in conflict handling, not in the permission design.
3. **Policy.** `tenancy/policy.py`: `CATEGORY_OF`: apply/package/import/reconcile -> `expand_permissions`; rotate/revoke -> `revoke_credential`. Mutating: apply, reconcile, rotate, revoke (admin
   credentials on the customer's cluster: always); package only if its policy goes beyond the monitor role; import only with a provision token; `plan_preview` is read-only. So a
   `monitoring_only` customer can use Mode B monitoring packages/import and read-only previews, nothing else; `customer_approval` customers need the customer link for mutating ones; extra approvals add
   distinct approvers. `deployment.*`/`guest.*` prefixes unchanged (no such actions exist on this branch). Provider models gained an optional `customer_id` (unbound clusters; default = MSP
   internal customer; must match the endpoint's customer); referenced previews/packages must belong to the same customer.
4. **Scoping.** `/providers/{id}/permissions`, `.../permissions/check` and `.../packages/{pkg}` apply operator customer scope (404 outside; artifacts carry `customer_id`; customer-less legacy artifacts
   migrate to the default customer).
5. **Alerts.** Drift and token-failure transitions also insert `notifications` rows for every enabled alert channel (once per transition, no secrets) in addition to audit.

## Known limits
- A Mode A apply plan waiting on a customer approval link outlives its 15-minute temporary credentials; it then fails with "credentials expired" and must be re-planned. Mode B (no admin creds) is the intended customer-approval path.
- The broker still does not enforce node/VMID/caps (see provider-provisioning.md). Real-cluster behaviour unverified.
- Mode A `provider.provision.apply` on `monitoring_only` customers is refused even for monitoring presets (use Mode B).
