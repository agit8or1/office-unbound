## Phase 1: what changed in the SSH bootstrap (review finding -> fix -> test)
| Finding | Fix | Test (`tests/test_lab_ssh_bootstrap.py`) |
|---|---|---|
| H1 fails open | Every terminal failure of `wait_enrollment`/`await_callback` runs `fail_closed`: seal (verified) if the guest ever proved itself, then **stop the VM**, clear the first-contact material from the VM config, wipe the secrets, audit `guest.bootstrap_failed_closed`. The persistent seal (script + timer + boot check, `OnActiveSec`/`OnBootSec` + a deadline file) is the **first thing** installed after the proof, before the user-data. Config errors are validated at `vm.configure` (before the VM boots). A fenced executor touches nothing. | `test_h1_*`, `test_arm_installs_a_persistent_timer_and_a_boot_check_before_anything_else` |
| H2 seal unreliable | Synchronous inside the authenticated session; the guest reports masked units / inactive sshd / locked account / no key / no sudo rule (MAC'd) AND the ICS probes TCP 22; audited (`guest.bootstrap_sealed` / `_seal_failed`); the resume path (node already exists) seals and then clears. | `test_seal_*`, `test_h2_*` |
| M1 deterministic secrets | Random per VM **instance** (deployment, vm, vmid): `guest_bootstrap` table (migration 0009b), vault-encrypted (AAD binds row + column), columns set to NULL after use; a re-created VM revokes and wipes its predecessor's record. Nothing derives from the signing key any more. | `test_bootstrap_material_is_random_per_instance_*`, `test_vault_context_binds_*`, `test_a_replaced_vm_instance_*` |
| M2 secret on argv / left in config | The HMAC key is read from sysfs **inside python3** (no `openssl -hmac "$S"`); the SSH command carries only a nonce and the base64 of a fixed body. After enrollment (or fail-closed) `configure_vm(clear_bootstrap=True)` removes the SMBIOS serial/sku/family (uuid kept), `sshkeys`, `ciuser`; `bootstrap_material_present` makes it idempotent. | `test_the_proof_secret_never_appears_on_a_command_line_*`, `test_configure_sets_sku_family_and_clears_the_bootstrap_material` |
| M3 root-exec primitive | `Guest._session` takes an operation **name** from a closed table (`OPERATIONS`); there is no caller-supplied body. | `test_only_fixed_operations_can_run_*` |
| M4 payload before proof | Each session prints `OU-PROOF = HMAC(secret, nonce)` first; the payload (user-data) is written to stdin only after it verifies; an impostor receives nothing and gets a non-retryable failure. | `test_the_payload_is_sent_only_after_the_guest_proved_itself` |
Deliberate behaviour change: after a fail-closed the VM's material is destroyed, so a **resumed create** of the same VM instance reports "bootstrap material is gone: destroy and re-create" instead of re-attempting (the previous implementation could retry because everything was recomputable, which was the M1 weakness).

## Phase 2: the production path (no SSH at any point)
### Flow
1. **Image** (`blueprints/build/guest-image/`, ADR-0008 recipe): Debian 12 `genericcloud` (Ubuntu 24.04 profile included, not built) fetched over HTTPS; the upstream `SHA512SUMS(.sign)` signature must verify against a key whose **full fingerprint is pinned by the operator out of band** (`os/<os>.env`, shipped empty: `recipe.sh fetch` refuses to run, test-covered) and the image hash must be in that signed file. `customize.sh` installs podman/nftables/python3-cryptography, our node agent **code only** (no keys, no certificate, no token), the rootless `ou-svc` user, `ou-bootstrap.service`, an nftables default-deny file (no inbound rule at all), masks SSH, deletes host keys, disables cloud-init, locks root; **no qemu-guest-agent** (ADR-0002 s7). `sbom.py` writes a CycloneDX SBOM; `recipe.sh manifest` writes `SHA256SUMS`; `recipe.sh sign` (offline release host, ECDSA P-256) writes `SHA256SUMS.sig`.
2. **Release verification** (`ics/ics/guest/golden.py`): operator-pinned release public key (SPKI SHA-256), manifest signature, exactly one image + its SBOM, hashes, no symlinks, closed file names. Tamper cases are test-covered.
3. **`image.import`** (`ProxmoxMutations.import_image`, `ImageImportSpec`): scope checks (node, pool, both storages, bridge), re-hash of the file, capability check on the storage (`import` content on the import storage, `images` on the target; the error text carries the owner command), multipart upload with `content=import` + `checksum-algorithm=sha256` (Proxmox re-verifies), `POST /qemu` with `scsi0=<target>:0,import-from=<storage>:import/<file>`, `POST .../template`; tags `ou-managed;ou-image`. Not part of the default probe verbs (`privileges.IMPORT_STORAGE_PRIVS` documents what the owner must grant).
4. **Clone time** (`vm.configure`): `bootstrap_config` issues a random per-VM-instance record and writes SMBIOS `serial = <bid 16 hex><secret 64 hex>`, `sku = https://<ics>:<port>`, `family = sha256:<ICS certificate pin>` (the plan-derived guest configuration is stored with the record). Needs `ICS_GUEST_CALLBACK_URL` and `ICS_GUEST_CALLBACK_PIN_SHA256`.
5. **First boot** (`ics/agent/ou_agent/firstboot.py`, `ou-bootstrap.service`, `Restart=no`): read SMBIOS (sysfs, never argv); generate agent key + TLS certificate + its own enrollment token (only the hash is armed); one POST to `/api/v1/guest-bootstrap/report` over TLS **pinned to the SMBIOS hash, checked before any byte is sent**, carrying address/port/TLS fp/key fp/token and `HMAC(secret, canonical)`; verify the ICS's `ack` (it must know the secret) and the MAC'd closed-schema configuration; then apply it (agent allowlist, image policy, polkit, nftables with the agent port to the ICS source only, start the agent). Any failure (bad SMBIOS, pin mismatch, bad ack, bad config) leaves the shipped state (default-deny, SSH masked, agent never started) plus a `failed` marker. Only transport errors are retried (<= 10 min); authentication failures are final.
6. **ICS endpoint** (`guest/callback.py`): minimal closed JSON, HMAC checked in constant time (dummy HMAC for unknown ids), source IP must equal the reported agent address, timestamp +-5 min, TTL (`ICS_GUEST_BOOTSTRAP_TTL_SECONDS`, 1800), **single use** (atomic `pending -> reported`; a second valid report = `guest.bootstrap_replay_alarm`, accepted nowhere), per-IP 12/min and global 120/min limits, one generic `401 rejected` for every failure, 429 when limited. The guest-generated token is held vault-encrypted until enrollment.
7. **Executor**: new plan step `guest.await_callback:<vm>` (kind `wait_guest_callback`) between `vm.start` and `agent.enroll`; it waits for the report and fails closed on timeout (stop VM, clear config, wipe secrets). `agent.enroll` enrolls over the pinned agent TLS with the guest's token and fingerprints (`_enroll`, unchanged), then clears the SMBIOS/ssh material from the VM config, deletes the secrets and audits `guest.bootstrap_completed`. The step is a no-op under the lab SSH bootstrap and for ports without it.

## Not done / limits (read before relying on any of this)
- **No real VM was bootstrapped by this path, no image was built or imported.** What the emulation cannot show: that Debian 12's `systemd`/`python3-cryptography` run `firstboot.py` as designed, that a real VM reads `product_sku`/`product_family` the way PVE writes them (`smbios1: base64=1,serial=..,sku=..,family=..` is documented PVE syntax; sysfs field names `product_serial|product_sku|product_family` are the kernel's), that the callback URL is reachable from the VM network, the agent's TLS SAN when DHCP changes the address, and Proxmox's behaviour for `import-from` on this storage layout.
- The golden image build recipe was syntax-checked and its refusals tested; it was **not run**. The upstream signing key fingerprints are deliberately **not pinned** in the repo (I did not fetch them: out-of-band verification is the operator's act). Ubuntu 24.04 has a profile only.
- The ICS certificate pin is the SHA-256 of the certificate the guest receives from the ICS HTTPS listener (leaf). Pinning a CA instead needs the guest to see the chain; not implemented. The ICS must expose the callback on a URL the VM network can reach (today the ICS API listens behind nginx; the owner decides which listener/port and sets `ICS_GUEST_CALLBACK_URL`).
- Review item "optionally cross-check the source IP's neighbour-table MAC with the Proxmox `net0` MAC" is not implemented (the source IP == reported address check is). Residual risk named by the review stands: a Proxmox principal with `VM.Audit` on the pool can read the one-time secret before the VM uses it and race the enrollment; it is detected by the replay alarm and bounded by the TTL; keep `VM.Audit` on `officeunbound-*` pools to the ICS tokens.
- The guest applies the ICS-supplied configuration (closed schema, MAC'd, validated again on the guest) but the ICS-side rendering of ports/registries still lives in `cloudinit.py`/`agentport._callback_config`; inter-VM firewall rules and `tls_trust` remain as listed in `first-real-deployment.md`.
- `ics/ics/guest/sshboot.py`, `GuestSpec.bootstrap_user` and the `fe80::/10` port-22 rule remain (lab). The review's "Phase 2" test that the ICS package has no SSH client invocation is a weaker check today (`test_the_guest_program_contains_no_ssh_*` only constrains the guest program and the other ICS modules).
- Phase 1 real-cluster re-verification on pve06 (hardened SSH path) was **not run**: after Phase 1 the default path is the callback, which cannot run on the stock template; the lab path would need `ICS_ENVIRONMENT=lab` + `ICS_LAB_SSH_BOOTSTRAP=true` and Z's reproduction recipe. Real guests found by cleanup check: none created, `[126, 131]` untouched (this session made no Proxmox call).

## OWNER PREREQUISITE (do not work around; run on pve06 as root)
pve06's `PVE06-Storage` is lvmthin (`images,rootdir`) and cannot hold an import image. Needed: a **directory** storage with `import` content, and rights for the provision token. The node-local `local` directory storage works:
```
pvesm status                                     # confirm `local` exists and is type dir
pvesm set local --content "$(pvesm config local | sed -n 's/^\tcontent //p'),import"       # adds `import`, keeps the existing content types
pveum role add OUImport --privs "Datastore.AllocateTemplate Datastore.AllocateSpace Datastore.Audit"
pveum acl modify /storage/local --tokens 'officeunbound@pam!ics' --roles OUImport         # (the provision token's id; adjust if different)
```
and in the ICS, add `local` to the endpoint's allowed storage. Existing grants already cover the rest (`VM.Allocate`, `VM.Config.*`, `Datastore.AllocateSpace` on `PVE06-Storage`, pool `officeunbound-pve06`). Then, on a builder: `blueprints/build/guest-image/recipe.sh debian-12 all` after pinning `UPSTREAM_KEY_FPR`/`UPSTREAM_KEY_FILE`, `recipe.sh debian-12 sign` on the release host, and set `ICS_GUEST_CALLBACK_URL` / `ICS_GUEST_CALLBACK_PIN_SHA256` in the ICS env file. Production `/etc/office-unbound/ics.env` was **not** touched by this session.

## Review 5 hardening (agent BA)
- `ICS_GUEST_REQUIRE_NIC_BINDING` (default true): the callback source address must resolve in the ICS host ARP table to the VM net0 MAC; set false only for routed guest networks (weaker binding).
- Callback limits: per source IP 12/min, per bootstrap id 30/min (reserved for known VMs), unknown ids share 60/min; the guest retries 429/503 with backoff within its 600 s budget. Body cap 4 KiB. A second valid report before enrollment fails the record and stops the deployment.
- Dedicated listener: `python -m ics.serve_callback` (`deploy/ics-callback.service`, `ICS_GUEST_CALLBACK_LISTEN`, default 127.0.0.1:8089) and `ICS_GUEST_CALLBACK_DEDICATED=true`; run it with one worker.
- Golden image import verifies the signed release itself and refuses older releases than the newest imported (template tag `ou-rel-<os>-<date>`); upstream builds are pinned by `UPSTREAM_SERIAL` in `blueprints/build/guest-image/os/*.env`.
