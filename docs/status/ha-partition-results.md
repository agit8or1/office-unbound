# HA two-controller partition proof - lab results, 2026-11-16 (agent CA, branch `ha-proof`)

Owner requirement: *"Do not consider HA complete until a two-controller test proves that only one controller can execute infrastructure operations."* and *"Prevent duplicate execution during network partitions and failover. Test actual primary/standby partition scenarios."*
Design: [ADR-0012](../adr/0012-ics-warm-standby.md), runbook [ics-recovery.md](../runbooks/ics-recovery.md). Earlier single-failure proof: [ics-standby-results.md](ics-standby-results.md).
**Evidence level (ADR-0000): Lab tested** (systemd-nspawn machines, a fake Proxmox - the pve simulator, a test double - and a stub backup helper; no real Proxmox, no production ICS). Raw evidence: [baseline](ha-partition-evidence-baseline.json) (code before the lease) and [lease](ha-partition-evidence-lease.json) (with the lease).

## Verdict
- **Without the lease** (fixes-r7 at 199419d: fencing = the controller's own database + the agent epoch) the requirement was **NOT met**: a partitioned old primary kept calling the provider, sending notifications and (until an agent refused it) driving agents after the new epoch was committed - for as long as its work mix contained no agent call, **without limit** (S2, S2b, S7, S8 FAIL).
- **With the lease** (fixes-r7 07e851d, witness on the standby host, T = 15 s in the lab) every scenario S1-S8b **PASSES**: after the new epoch is committed the old primary performed **zero** provider calls, agent calls, backup runs, webhook sends, enrollments or job executions, and no job or step ran twice across the two controllers. The price is the promotion time (it waits `T + margin` for the old lease to expire) and that a primary whose witness is unreachable stops working (that is the point; the audited override exists).
- Residual risks are listed at the end (replication-gap jobs, new primary without a second party, harness limits). They are findings, not hidden.

## How it is measured (every assertion is on a central recorder, not on controller logs)
Machines: `ou-ha1`, `ou-ha2` (controllers; roles swap between scenarios, the old primary is rebuilt as the standby with the documented `--standby-of ... --rebuild`), `ou-ha-node1` (one real node agent + the recorder). MemoryMax 1.5 G / 1.5 G / 1 G, host `MemAvailable` checked >= 2 GiB before every start (7-9 GiB observed).
| Side-effect class | Where it is observed | How the controller is identified |
|---|---|---|
| provider calls (read and mutating) | fake Proxmox in the recorder (`tests/pve_sim.py`, TLS, pinned fingerprint), mutating calls slowed to 1-2.5 s so jobs are long-running | source address + `X-OU-Controller`, `X-OU-Epoch`, `X-OU-Job` headers (new: stamped by `egress.hooks()` on every provider/notification client) |
| notifications | webhook receiver in the recorder (TLS, pinned) | same headers |
| agent calls (runbooks, announce, epoch learning) | the node agent's new **exec log** (`/var/lib/ou-agent/exec.log`: one secret-free line per request: peer, job id, controller epoch, decision) | peer address + request epoch |
| backup runs | the real agent admits `backup.run`; a stub of the root helper `ou-backup` logs every run it is started for | via the agent exec log (admitted `backup.*`) |
| enrollment | agent exec log (`enroll` lines) | peer address |
| credential operations | provider token rotation (`provider.token.rotate`: mutating calls at the provider) | headers |
| console / API mutations | HTTP `POST /api/v1/plans` against the old primary: status + `X-OU-Role`; `/readyz` | - |
| promotion instant | `controller_state.changed_at` of the NEW primary (the commit of epoch+1) | - |
Work is created through the real typed-plan path (`actions.create_plan` + `decide_plan` approvals, as the API does) and executed by the running service's own worker / monitor / backup-scheduler / inventory loops; the harness itself performs no side effect. A scenario whose old primary was not demonstrably active before the test is reported INVALID, never PASS.

Lab settings: `wal_sender_timeout = wal_receiver_timeout = 5 s` (default 60 s: see timings), lease T = 15 s, renew 3 s, witness margin 5 s (production defaults are T = 30, margin 10). Observation after commit: 45 s (S2b: 90 s).

## Timings (lab; machines on one host, one node)
- Partition detected by the standby (WAL receiver no longer `streaming`): **5.0-6.2 s** with `wal_receiver_timeout = 5 s`. **With PostgreSQL's default (60 s) the promote command refuses "still streaming" for up to 60 s after a partition**; set it deliberately (the lab value is not a recommendation for flaky links).
- Promotion command: 3.6-4.8 s without lease; **11-23 s with lease** (it waits until `T + margin` has passed since the last grant; here 20 s). With the production defaults (T = 30, margin 10) expect >= 40 s.
- RTO measured from stopping the old primary to the first request the agent executed for the new primary: 4.3 s without lease (earlier proof: 4.4 s), **20.7 s with lease** (T = 15 / margin 5). RPO unchanged (replication lag < 1 ms idle).

## Findings and what was done
- **F1 (High, fixed by agent BU, verified here)**: DB-only fencing cannot stop a partitioned primary (S2/S2b/S7/S8 baselines). The witness lease closes it; promotion proves the old lease expired before bumping the epoch. See the table.
- **F2 (fixed on `ha-proof`, test `tests/test_ha_evidence.py`)**: in lease mode a process without the renewal thread (`ics.cli epoch-attest`, the announce step of `promote`, lab scripts) built a lease that was never granted, so the operator could not sign an epoch re-seed document ("controller lease expired") although the witness was reachable. `Lease.require()` now renews on demand for such processes (`on_demand`, set by `lease.build`); a partition still refuses them.
- **F3 (egress evidence, added on `ha-proof`)**: provider and webhook calls now carry `X-OU-Controller`, `X-OU-Epoch`, `X-OU-Job`; the node agent writes an exec log. Both are what makes the proof independent of the controllers' logs and are useful in production incident work. The provisioning admin client was already under the guard (it shares `_request`); a test now pins that.
- **R1 (residual, to the lead)**: jobs claimed or queued inside the replication gap. In the S2 lease run the agent refused two `replay_job` requests from the NEW primary (a `service.status` and a `backup.run` job id the old primary had already executed before the partition): the new primary re-claimed jobs that its replica still showed as queued. The agent's single-use job journal stopped those. **Provider mutations have no equivalent replay protection** (no idempotency key at the provider): such a duplicate would execute. Not observed at the provider in S4 (no job id seen from both controllers), but not excluded by design. Suggested fix: at promotion mark every job that was queued/running in the replica as "uncertain" (never auto-run; operator re-queues), as `reap_expired` already does for running jobs.
- **R2**: a job in flight at the lease expiry stops at its next side effect and ends `failed` with a partial result (e.g. half of a provisioning apply). That is the intended at-most-once behaviour; recovery is the operator's (the plans are not idempotent).
- **R3**: after a promotion the new primary's lease points at the witness on its own host (the key-bundle copy of the old primary's env); it has no second party until the old primary is rebuilt as a standby. The lab harness reconfigures this after each rebuild; the runbook should say so (and that a standby that is only an ICS process dying but whose witness unit lives keeps the primary alive: S8 stops the whole host).
- **R4 (harness limits)**: one node agent; a stub backup helper (no real restic/rest-server); the provider is a simulator, so a real Proxmox's own idempotency/locking is not exercised; clocks are one host's. Enrollment of a NEW agent by the old primary was not driven (only guarded in unit tests `test_review7_fencing`); the enrollment class in the tables is 0 because no enrollment was attempted by the harness. Customer-facing address/DNS cut-over is not part of this proof.

## Re-running (repeatable)
`blueprints/lab/ha/partition-test.sh up | deploy | run [S1 S2 S2b S4 S5 S6 S7 S8] | down` (needs sudo on the lab host; `HA_LEASE=0` removes the lease configuration = baseline; `HA_LEASE_SECONDS`, `HA_OBSERVE_SECONDS`, `HA_EVIDENCE`). `deploy` pushes the checkout, re-stamps old lab databases (`alembic_version` 0012 -> 0012r7) and restarts. After `git merge fixes-r7` run `deploy` then `run`. Each scenario ends with the old primary rebuilt as the standby on the next `ensure_pair`; a harness bug that picked a stale (never fenced) primary once destroyed a promoted database - it now picks the highest epoch.
**Rebuild from nothing** (what was done for this proof): `blueprints/lab/common/create-machine.sh ou-ha1|ou-ha2|ou-ha-node1 ou-base-noble <ip> <MemoryMax> start`; `push.sh`; `bootstrap.sh --listen-ip .52 --allow-cidr 192.168.186.0/24 --admin alice` on ha1 (needs `VERSION`, `VERSIONS.json`, `blueprints/catalog` next to `ics/`); `node-setup.sh <ip>` on the node; enroll + seed with `ha_seed.py seed` (users, node, provider via preview+apply, webhook channel, check, backup policy); `ics-standby-prepare-primary.sh` on ha1 and `bootstrap.sh --standby-of` on ha2; `ICS_ALLOW_LOOPBACK_ENDPOINTS=true` in `ics.env` (the simulator advertises the test-double marker).
