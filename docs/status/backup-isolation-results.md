# Backup isolation results (agent AU, 2026-11-15, lab)

Closes the T20 backup FAIL (B02 in [tenant-isolation-results.md](tenant-isolation-results.md): "archives are plain tar, not encrypted under a per-customer key") with the real backup product of [ADR-0010](../adr/0010-backup-product.md), and adds the ICS controller tier (skipped by [backup-product-results.md](backup-product-results.md)). Status values per ADR-0000: per-customer boundaries and the controller tier are **Lab-proven** (executed evidence below, dev ICS only); production topology (separate stores, S3 prefixes, runner per customer) is **Planned**.

## 2. Per-customer isolation: T20 section `backup` (executed, 61 PASS / 0 FAIL)

## 4. Findings fixed on the way
1. **The template unit `ou-rb-backup@.service` made `setuid()` fail** for any hook that switches user: `NoNewPrivileges` together with `ProtectKernelModules`/`ProtectKernelTunables`/`LockPersonality` gave `runuser: cannot set user id` (and `sudo ... PERM_SUDOERS`); bisected with transient units (NNP + `ProtectHome` + `PrivateTmp` is fine). The three directives were removed from the template; the ICS hook uses `/usr/sbin/runuser` instead of `sudo`.
2. `id-restore.sh` assumed the main lab's realm and CA path; a customer stack (realm `custa`) could not be verified. Now parameterised (`restore_env` OU_REALM/OU_DOMAIN in the root-owned tier config), uses the CA restored from the backup, and gives the scratch machine its own names in `/etc/hosts`.
3. The old B02 design flaw: lab scripts left a plain tar per customer in a root-only directory. The product never writes a plain archive outside the root-only staging directory of the run (removed afterwards, checked in B40).
4. `backup.*` were all "mutating" in the tenant policy, so every scheduled run of a customer-owned stack would have created a customer approval draft; reclassified (see section 1).
5. Stale runner profiles of earlier lab runs correctly collide with the helper's machine-claim check (a cleanup step now runs at the start of the T20 section).
6. The audit-head evidence of the ICS manifest is read before the dump (not after), so an online backup of a live controller can still be verified: the restored chain must contain that event with that hash.
7. The result details `chain_checked`, `passive`, `operator_login` were dropped by the ICS result whitelist; added.

## 5. Limits and open items
- One rest-server instance and store per site with `--private-repos` is path separation inside one process; for production use a store (or instance, or S3 bucket/prefix with scoped keys) per customer and place it outside any shared blast radius. The lab has one `ou-bkp1` for both customers (the encryption boundary and the REST authorisation hold independently, B11/B12).
- The runner host in the lab holds both customers' profiles (one agent, one host root): the helper isolates them logically (own config, credentials, staging, machines) but a compromised runner root reads both customers' repository passwords. Production: a runner node per customer (or per tier group) with only its own profile in the agent allowlist.
- Identity tier only for the per-customer restore drill (files tier of the customer stacks was running for the full T20 but its restore verification into per-customer scratch machines was not added); canaries were seeded by the test (LDAP entry `drillcanary`, Keycloak realm role `drill-canary-t20-<a|b>`).
- Customer-owned (`customer_approval`) customers still need a customer approval for prune and restore verification (by design); the lab customers were MSP-owned (`auto`).
- ICS controller tier: dev ICS only. The production controller needs `/etc/ou-backup/ics.json` without `backup_env`, a viewer-role login canary account and a scratch machine; no run against the production service was made (deliberate). The restore verification does not exercise the cut-over or agents accepting the restored controller (same limit as the existing drills). The scratch image had its packages from an earlier ICS restore (pip cache warm): a cold apt/pip install adds minutes to the RTO.
- `ou-rb-backup@.service` is a lab-installed copy of the repo unit (host-changes).
