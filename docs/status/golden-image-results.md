# Golden guest image: build, trust anchors, boot proof (agent AT, 2026-11-15)

Branch `golden-at` (from `bootstrap-v2`). Status vocabulary: ADR-0000 / ADR-0009 s8.
Everything below was **executed** in the isolated builder nspawn machine `ou-img1` (clone of `ou-base-noble`, zone `oulab`, `PrivateUsers=pick`, `MemoryMax=2G`) and on the ICS host (signing only). **Nothing was imported into, or created on, Proxmox** (the owner has not enabled `import` content on pve06; the production `ics` service and database were not touched).

## 1. Upstream trust anchors (authoritative, cross-checked, recorded in `os/*.env`)

### Debian 12 (bookworm): no cloud-image signature exists
* `https://cloud.debian.org/images/cloud/bookworm/latest/` (and the dated directories `20261112-2660/`, `20261026-2643/`, `trixie/latest`, `bullseye/latest`, `bookworm/daily/latest`) contain `SHA512SUMS` but **no** `SHA512SUMS.sign` (HTTP 404 on every one checked). Only the legacy `OpenStack/` directory still carries `SHA512SUMS.sign`.
* `https://cloud.debian.org/images/cloud/` states: "For the current official images ... the safest method is to download the image and checksum files over TLS from cloud.debian.org or cdimage.debian.org. These names support DNSSEC ... The legacy OpenStack images ... provide checksums and signatures." So the old recipe's `UPSTREAM_KEY_FPR`/`SHA512SUMS.sign` verification could never have worked for the image it names. **A fingerprint for "the Debian cloud image signing key" cannot be pinned because there is none; I did not invent one.**
* What Debian does sign authoritatively is the **archive**. The Debian profile therefore builds the rootfs with `mmdebstrap` from the signed archive; the Release files are verified against pinned **primary** key fingerprints:

| Key | Full fingerprint | Source 1 | Source 2 | Source 3 |
|---|---|---|---|---|
| Debian Archive Automatic Signing Key (12/bookworm) | `B8B8 0B5B 623E AB6A D877 5C45 B7C5 D7D6 3509 47F8` | https://ftp-master.debian.org/keys.html ("archive signing key") | `debian-archive-keyring` 2023.4ubuntu1 (`debian-archive-bookworm-automatic.gpg`, fetched with `apt download` from the Ubuntu archive, i.e. a different trust chain) | live `https://deb.debian.org/debian/dists/bookworm/Release.gpg`: signed by its subkey `4CB5 0190 2074 7A3F ...`, `gpgv` "Good signature" |
| Debian Stable Release Key (12/bookworm) | `4D64 FEC1 19C2 0290 67D6 E791 F8D2 585B 8783 D481` | ftp-master keys.html ("Stable Keys") | debian-archive-keyring (`...-stable.gpg`) | live Release.gpg: "Good signature" |
| Debian Security Archive Automatic Signing Key (12/bookworm) | `05AB 9034 0C0C 5E79 7F44 A8C8 254C F3B5 AEC0 A8F0` | ftp-master keys.html ("security archive signing key") | debian-archive-keyring (`...-security-automatic.gpg`) | (security archive, used for `bookworm-security`) |

`recipe.sh` refuses (exit 4) if a key file's primary fingerprint is not in `ARCHIVE_KEY_FPRS` or if a pinned one is missing; apt/mmdebstrap then verify every Release against exactly this keyring (`signed-by=`), and the shipped image keeps the same pinned keyring for its own updates.
* Image-hash cross-check of the unsigned upstream image (not used for the build, recorded for the record): `SHA512SUMS` of `20261112-2660`.

### Ubuntu 24.04 (noble): signed checksums, pinned
* `SHA256SUMS.gpg` of `https://cloud-images.ubuntu.com/noble/current/` (made 2026-10-17) verifies with **`D2EB 4462 6FDD C30B 513D 5BB7 1A5D 6C4C 7DB8 7C81`**, "UEC Image Automatic Signing Key <cdimage@ubuntu.com>" (RSA 4096, keyid `1A5D6C4C7DB87C81`).
* Sources: (1) `ubuntu-keyring` 2023.11.28.1 (`/usr/share/keyrings/ubuntu-cloudimage-keyring.gpg`, `dpkg --verify` clean); (2) `https://keyserver.ubuntu.com/pks/lookup?op=get&search=0xD2EB44626FDDC30B513D5BB71A5D6C4C7DB87C81` returns the same primary fingerprint; (3) `https://wiki.ubuntu.com/SecurityTeam/FAQ` ("The Ubuntu Cloud Images checksums are signed with key: ... Key fingerprint = D2EB 4462 6FDD C30B 513D 5BB7 1A5D 6C4C 7DB8 7C81"). The key file is shipped in `keys/ubuntu-uec-image-signing.asc` and its fingerprint is checked against the pin on every run.
* Executed in `ou-img1`: `recipe.sh ubuntu-24.04 fetch` then `verify` -> "noble-server-cloudimg-amd64.img: OK / upstream image verified (signature by the pinned key + checksum)". Refusals proven (exit 4): wrong pin, tampered `SHA256SUMS` (signature fails), tampered image (checksum fails) in the builder and offline in `tests/test_golden_image.py`.
* Note: the endpoints `cloud.debian.org`, `cloud-images.ubuntu.com`, `ftp-master.debian.org`, `keyserver.ubuntu.com`, `wiki.ubuntu.com` are public read-only sources; only `deb.debian.org` is itemised in `authorized-endpoints.md` (read-only anonymous GETs, nothing sent).

## 2. Build method, evaluated and chosen
| Candidate | Result in `ou-img1` |
|---|---|
| `virt-customize` / libguestfs | needs the supermin appliance + KVM or a slow TCG appliance and `/dev/kvm`/fuse; not viable unprivileged (and TCG appliance boot would double the build time) |
| `qemu-nbd`, loop mount | needs `nbd`/`loop` kernel modules and `CAP_SYS_ADMIN` in the init userns: **not available** in an unprivileged nspawn (`PrivateUsers=pick`) |
| `debootstrap` | `mknod` for /dev fails in the user namespace |
| **`mmdebstrap --mode=root` in a private mount namespace + `systemd-repart` + `mkfs.ext4 -d`/`mcopy` + `syslinux --offset` + `qemu-img convert`** | **works**, no mount/loop anywhere. Chosen. Lesson recorded: running `mmdebstrap` without `unshare -m` turned the machine's cgroup mount read-only (needed a machine reboot); the recipe runs it under `unshare -m --propagation private`. |

Disk layout: GPT, p1 FAT32 `/boot` (256 MiB, kernel+initrd+loader, flagged legacy-bootable, syslinux installed into it at its offset; also `systemd-boot` at `EFI/BOOT/BOOTX64.EFI`, so both SeaBIOS and UEFI can boot), p2 ext4 root (last, grown at boot by `ou-growroot.service` to the disk size the ICS sets with `vm.resize`). Fixed partition UUIDs (`root=PARTUUID=`). `image.import` creates `scsihw=virtio-scsi-single`, `scsi0`, serial0, default (SeaBIOS) BIOS: the image matches that (no OVMF needed). The kernel is `linux-image-cloud-amd64` (6.1.0-55).

Image content (checked on the final tree in `ou-img1`): **no `sshd`** (`openssh-server` not installed; `ssh.service`/`ssh.socket` masked as a second line), no host keys, root `!*` locked, 0 accounts with an empty password, `ou-svc` locked/nologin with subuid/subgid + linger, `cloud-init` installed but disabled (`/etc/cloud/cloud-init.disabled`, NoCloud/None datasources, no ssh/users), `qemu-guest-agent` **not** installed, nftables default-deny (policy drop on input and forward; the first-boot unit replaces the file with the ICS-authenticated ruleset opening the agent port to the ICS source only), `ou-node-agent` installed **not enabled**, `/etc/ou-agent` and `/var/lib/ou-agent` empty (no keys/certificate/token), empty `/etc/machine-id`, unattended-upgrades limited to `Debian-Security` of bookworm, `Automatic-Reboot "false"` (the ICS schedules reboots), apt sources pinned to the archive keyring, `ou-release.gpg` present for the real channel. systemd-networkd DHCP.

Defects found by actually booting it (both fixed): (1) the shipped `nftables.conf` (`meta l4proto ipv6-icmp`) does not even parse on a minbase Debian: `/etc/protocols` (package `netbase`) was missing and `nftables.service` failed; the build now installs `netbase` and runs `nft -c` on the file as a build gate. (2) `mmdebstrap` cgroup/mount leak (above).

### Agent from the signed repository (no `curl | sh`)
`agent-deb/build-deb.sh` builds `ou-node-agent_0.1.0-ou1_all.deb` from `ics/agent` (reproducible: two builds gave the identical sha256 `68e19d99c755...`), `agent-deb/publish-dev.sh` admits it to the `dev` ledger and has the repo metadata signed **through `sudo -u ou-release /usr/local/sbin/ou-release-sign`** (security review 4: the build user never touches the key; `admit dev` and `sign dev`, the signer re-verifies hashes/ledger and sets Valid-Until). In the image, `customize.sh` compares the repo release key's fingerprint with `keys/ou-release-lab.FINGERPRINT` (`5D2750D022E0218361518491CE58A8B691F84C1B`) before it dearmors it into `/usr/share/keyrings/ou-release.gpg`, and apt installs `ou-node-agent` with `Signed-By` that keyring from the repository. The package is only code (no keys, unit not enabled). Not done: promote dev -> staging -> stable (needs an `install-smoke` test record and an approver, i.e. the owner's process); the image installs from `dev` because that is the only suite the agent is in. The repo serving URL for production is the owner's decision (the file repo was used for the build).

### SBOM and licences
`syft` 1.57.1 downloaded from the pinned URL and checked against the pinned sha256 (`bf52519e...`; same pin as `blueprints/build/tools.env`) scans the final root tree; the CycloneDX SBOM keeps package components only (13,938 per-file hash entries and 1,122 per-module kernel entries removed, the latter belong to `linux-image`) and carries the licence-scan summary in its metadata (so the signed manifest covers it). `licensescan.py` classifies every declared licence against `license-policy.yaml` (the pipeline's allow list): 293 components, 113 allowed, **0 denied**, **180 "review"**: nearly all are Debian copyright files that union many licence names (for example `bash`: `BSD-4-Clause-UC AND GFDL-1.3-only AND ... AND permissive`) or bare names such as "GPL"/"MIT License"; they are listed in `golden-image-evidence/licenses.json` for the owner's review, **not silently accepted**. No component is proprietary/non-commercial/source-available. Vulnerability scan (osv-scanner) was not run for the image (not part of this task's list; `blueprints/build/tools.env` has the pinned tool).

## 3. Boot proof without KVM
Host has no `/dev/kvm`; `qemu-system-x86_64 -accel tcg` ran inside `ou-img1`. Harness `bootproof/bootproof.sh` + `bootproof/ics_side.py`:
* The ICS side is a **throw-away real ICS runtime** inside the builder (local PostgreSQL database `ics_proof`, own vault/audit keys, own TLS certificate; never the production service): alembic head, `bootsecrets.issue` (a real per-VM-instance record with a guest configuration), the real `callback` endpoint through `create_app`, served over TLS.
* SMBIOS fields `serial` (bid + 64-hex secret), `sku` (`https://10.0.2.2:8445`), `family` (`sha256:<cert pin>`) are passed with `-smbios type=1,...` (what Proxmox `smbios1` provides); the image boots through a copy-on-write overlay.
* Sequence executed (`golden-image-evidence/pos-ics.log`): VM boots (SeaBIOS -> syslinux -> kernel -> systemd, ~90 s total wall clock under TCG, 22:52:08Z-22:53:39Z) -> `ou-bootstrap.service` reads SMBIOS from sysfs, generates keys/TLS cert/token, POSTs the report over TLS pinned to the SMBIOS hash -> the real endpoint verified the HMAC, nonce/timestamp, TTL and single use (state `pending` -> `reported`, audit `guest.bootstrap_report`) -> the guest verified the ICS's HMAC acknowledgement and MAC'd configuration, applied nftables/agent config and started `ou-agent` -> the ICS reached the guest agent (port-forwarded 127.0.0.1:18443 -> guest 8443; the guest's nftables allows 8443 from `10.0.2.2/32` only, which is where the forwarded connection comes from) over TLS **pinned to the fingerprint the guest reported**, checked that the agent key matches the reported fingerprint, `agentclient.enroll` with the guest-generated token succeeded (agent 0.1.0) -> record `enrolled`, all secret columns NULL (`secrets_wiped: true`).
* Emulator artefacts, stated plainly: (1) user-mode NAT makes the ICS see the guest as 127.0.0.1 while it reports 10.0.2.15; the endpoint's "source address == reported address" check is satisfied by patching `callback.source_ip` in the harness (every other check unmodified); (2) the ICS-side enrollment/wipe calls the same functions the executor uses (`agentclient.identity/enroll`, `bootsecrets.delete_secrets`) but the full executor plan (`guest.await_callback`, `agent.enroll` steps, Proxmox `configure_vm(clear_bootstrap=True)` removing the SMBIOS values from the VM config) was not run: there is no Proxmox here and the fake-provider version is covered by `tests/test_guest_callback.py`; (3) SMBIOS values stay in the emulator command line (they would be removed from the PVE VM config by the ICS).
* Negative run (`FAMILY_OVERRIDE=sha256:...07`, i.e. the ICS certificate does not match the pin in SMBIOS): the guest booted to its login prompt, but within a 300 s window (the positive run took 91 s) no report was accepted: the record stayed `pending` (`golden-image-evidence/neg-ics.log`); the guest's unit fails closed on a pin mismatch before any byte is sent (unit-tested in `tests/test_guest_callback.py`; here the failure is seen from the ICS side only, the guest-side `failed` marker was not read out of the VM).

## 4. Signing (dedicated signers, no NOPASSWD ALL used for signing)
* Packages: existing `ou-release-sign` (GPG, suite ledgers) as above.
* **Images (new): `blueprints/build/guest-image/signer/ou-image-sign` + `install-image-signer.sh`**, same pattern as security review 4: system user `ou-imgsign`, passphrase-protected P-256 key in `/var/lib/ou-imgsign` (0700), program in `/usr/local/sbin` (root-owned), sudoers rule `administrator ALL=(ou-imgsign) NOPASSWD: /usr/local/sbin/ou-image-sign *` (no shell, no other command). `sign` receives a tar of the image and SBOM, **re-computes both hashes itself** (the builder's word is not trusted), refuses unless a passing `first-boot` test record keyed by the image's SHA-256 exists (`record-test`, written after the boot proof), checks the SBOM is a CycloneDX inventory, builds the exact two-line `SHA256SUMS` and prints `SHA256SUMS` + base64-DER `SHA256SUMS.sig`. Covered by `tests/test_golden_image.py` (no record, failed record, extra tar member, non-CycloneDX SBOM, different image, success verified by `ics.guest.golden.verify_release`).
* Public key / pin to set in the ICS (lab key, **generated here**): SPKI SHA-256 `1756953ac4503f01fd1a08968fefef2e5f6712a542d42a21b634892a60eff1ec`.
* Signed release in `ou-img1:/var/tmp/ou-guest-image/out/`: `SHA256SUMS` (image `690d6514c896...`, SBOM `d7b15d56fb79...`) + `SHA256SUMS.sig` (copies in `golden-image-evidence/`), written after `record-test ... first-boot pass` for the booted image's SHA-256, and **verified with `ics.guest.golden.verify_release`** against the signer's public key pin above: accepted.
* Limits (same as the package signer, security review 4 "Limits"): while `administrator` keeps `NOPASSWD: ALL` sudo, the separation is on paper (that user can read the passphrase file or run `openssl` as `ou-imgsign`); production signing must be an offline host or HSM and the pin re-confirmed by the owner. The lab key is **not** a release key.

## 5. Owner prerequisite for `image.import` (do not work around; run on pve06 as root)
`privsep` API tokens have **effective permissions = the intersection of the user's and the token's permissions**, so BOTH grants are needed. `local` is a directory storage; `import` is a content type that must be added without dropping the existing ones.
```
pvesm status                                              # confirm `local` exists and is type dir
pvesm config local                                        # note the current `content` list
pvesm set local --content "$(pvesm config local | sed -n 's/^\tcontent //p'),import"     # keeps existing types, adds import
pveum role add OUImport --privs "Datastore.AllocateTemplate Datastore.AllocateSpace Datastore.Audit"
pveum acl modify /storage/local --users  'officeunbound@pam'      --roles OUImport      # the USER (privsep intersection)
pveum acl modify /storage/local --tokens 'officeunbound@pam!ics'  --roles OUImport      # the TOKEN
pveum user token permissions 'officeunbound@pam!ics' --path /storage/local               # must list the three privileges
```
(Adjust the token id if the provision token is not `officeunbound@pam!ics`.) Existing grants already cover the rest (`VM.Allocate`, `VM.Config.*`, `Datastore.AllocateSpace` on the target storage, pool `officeunbound-pve06`); add `local` to the endpoint's allowed storage in the ICS. Then in the ICS env: `ICS_GUEST_CALLBACK_URL` (an HTTPS URL reachable from the VM network), `ICS_GUEST_CALLBACK_PIN_SHA256` (the SHA-256 of that listener's certificate), the release key + pin for `image.import`. UEFI is not required (SeaBIOS boots the image); if the owner prefers OVMF the image already contains `systemd-boot` at `EFI/BOOT/BOOTX64.EFI` (not boot-tested).

## 6. Not done / limits (honest list)
* **Not VERIFIED-ON-REAL-INFRA.** TCG emulation of the real image is strong evidence for the kernel/initrd/systemd/first-boot path, not evidence for Proxmox's `import-from`, PVE's SMBIOS rendering (`smbios1 base64=1`), the VM network, DHCP address changes versus the agent TLS SAN, virtio-scsi on the real host, or `ou-growroot` on a resized disk (not exercised: the overlay is the same 4 GiB).
* The Ubuntu 24.04 image is verified but **not built** (customising a cloud image needs a loop mount / libguestfs; the same mmdebstrap method could build noble from the Ubuntu archive with `ubuntu-archive-keyring` pins: follow-up).
* Debian: the recipe is not bit-reproducible (it is not pinned to snapshot.debian.org: package versions are the bookworm point release of the day, recorded in the SBOM); `SOURCE_DATE_EPOCH` only names the image.
* 180 licence "review" items and vulnerability triage of the image are open; `unattended-upgrades` was configured but not exercised (no time in the TCG run).
* `systemd-boot`/UEFI path untested; syslinux (BIOS) path tested.
* The `dev` channel suite holds the agent; promotion to `stable` needs the owner's approval flow. The ledger of the production signer got one new entry (`ou-node-agent_0.1.0-ou1_all.deb`) in `dev`.
* The signer user/sudoers rule was installed on the ICS host (see host-changes); it is a lab arrangement.
* The ICS's `callback` endpoint assumes it sees the guest's real source address; behind NAT/proxy the `ICS_TRUSTED_PROXY` setting applies as designed (not exercised here).
