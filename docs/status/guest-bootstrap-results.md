## Design decisions
- **The enrollment token is never in user-data.** The ICS generates it and gives the guest only its SHA-256 (`OU_ENROLL_TOKEN_SHA256` -> `ou-agent init --token-sha256 --ttl`); the agent already stores only a hash. So the secret is in no user-data, hypervisor snippet, `/var/lib/cloud`, cloud-init log or install log (lab check: grep for the token over `/var/log /var/lib/cloud /var/lib/ou-bootstrap /etc/ou-agent` found nothing). `enroll.json` is 0600 and the agent deletes it on enrollment (existing behaviour, re-verified). The agent's public pins (TLS + key fingerprint) go to `/var/lib/ou-bootstrap/fingerprints.json` and the console for the ICS/operator (a hypervisor guest-agent read is **Planned**).
- **Rootless Podman as a dedicated user `ou-svc`** (nologin, locked, home `/var/lib/ou-svc`, explicit subuid/subgid, linger). The agent never calls podman. `podman.*` runbooks run through the fixed template `ou-rb-podman@<rid>.service` with `User=ou-svc` (**not root**), started via a polkit rule generated from the root-owned agent.json (same mechanism as the identity runbooks). The agent spools the validated, non-secret request in `/run/ou-agent-spool/<rid>.json`; the helper `python3 -m ou_agent.guesthelper` **re-validates it with the same code** against `/etc/ou-agent/agent.json` (tampered spool refused: unit-tested). Only `pkg.install_pinned` has a root helper (`ou-rb-pkg@.service`). `server.py` (review H1 fix) is untouched; `test_idle_tcp_connection...` still passes.
- **Image verification: sigstore keys through the containers/image policy** (`sigstoreSigned`), not `podman image trust` (GPG) and not the cosign CLI. Why: native in podman 4.9 / skopeo 1.13 (noble packages, no extra binary to pin), key based (no Fulcio/Rekor/online dependency, ADR-0007), signatures are registry attachments (no lookaside server), compatible with `cosign sign --key` (same payload, ECDSA P-256 pair), and one root-owned `policy.json` states "default reject; only these registries; only this key". `podman.pull_verified` passes `--signature-policy /etc/ou-agent/image-policy.json` explicitly, so the service user's own `~/.config/containers/policy.json` is not consulted; `registries.d` enables `use-sigstore-attachments` only for the allowlisted registries. Policy and the pinned key `/etc/ou-agent/image-signing.pub` are root-owned and generated by `render_image_policy.py`; the key's SHA-256 is pinned in the render spec and checked at render time. After the pull the digest is re-read and compared and a marker `verified/<digest>.json` is written; `deploy_unit` refuses images without that marker (an image put into storage any other way cannot be deployed) and never pulls implicitly.
- **Unit spec** (closed schema, unknown fields refused on both sides): component/name, `type` container | container-hostnet (host network only by that explicit type, and then no ports), digest-pinned image from allowlisted registries, env (tight charset), ports (explicit IPv4 bind, host port >= 1024), **named volumes of the component only** (mount path restricted: no `/run /proc /sys /dev /etc ...`), secrets by podman-secret name (values never pass through), read_only default true, memory. Always emitted: `NoNewPrivileges`, `DropCapability=ALL`, a per-component `.network`. No field exists for args, privileged, devices, host paths or sockets, and the text comes from a fixed template.
- **pkg.install_pinned**: names allowlisted in agent.json, **exact versions** (no ranges/wildcards, no downgrades), private apt config (`Dir::Etc::sourcelist=/etc/ou-agent/apt/sources.list`, own lists dir, sourceparts disabled, insecure repos disallowed) so only the listed repos are used; before every run each key in the root-owned keyring dir must be in `pinned-fingerprints` (else `repo_key_mismatch`); the installed version is read back and compared.
- **Firewall**: nftables inet, input policy drop; allows loopback, established, ICMP/ND/DHCP, the agent port from `mgmt_sources` (required), 22 only when a break-glass key exists, and the declared ports (optional source CIDRs); forward drop; syntax checked in tests and before applying. **Updates**: unattended security origin only, never auto-reboot. **SSH**: disabled and masked by default; with a key: key-only user `ou-admin`, `AllowUsers`, no passwords, no root. No password anywhere (`lock_passwd`).

## Rootless Podman inside systemd-nspawn (investigation)
It works, with two lab-only accommodations a real VM does not need:
1. nspawn's seccomp filter blocks `keyctl/add_key`, so crun fails (`create keyring: Operation not permitted`). Lab fix inside the guest: `/etc/containers/containers.conf.d/ou-lab-nspawn.conf` with `keyring = false` (no extra nspawn privilege).
2. nspawn overmounts parts of `/proc`, so a nested user namespace cannot mount a fresh procfs (`mount proc to proc: Operation not permitted`). `SYSTEMD_NSPAWN_API_VFS_WRITABLE=1` cannot be combined with `PrivateUsers=pick` (nspawn refuses to start; tried and reverted). Lab fix: guest unit `ou-lab-nspawn-proc.service` runs `mount -t proc proc /proc` early (the container's own pid namespace; nothing on the host changes).
Also: `useradd` allocates subuid 100000+, outside the 65536 ids an nspawn machine owns, and podman silently falls back to a single-id mapping; the bootstrap now replaces the range with the declared one (lab 20000-59999). The rootful-in-container fallback was therefore **not needed**. The lab registry is plain HTTP on 127.0.0.1 (`registries.conf.d/ou-lab.conf insecure=true`, lab only; the signature policy is unaffected).
Defects found by the lab and fixed in code: (a) the agent's UMask 0077 made the spool file unreadable for the helper; (b) the agent cannot delete result files in a helper-owned directory (helpers prune results older than 10 min; the agent now answers signed `error/exec_failed` if a helper produced no result instead of an empty "ok"); (c) `NoNewPrivileges=true` on the pkg unit broke apt's `file:` method in nspawn (removed, commented); (d) gpg needs a writable GNUPGHOME (throw-away temp dir); (e) `useradd`'s default subuid range (above).

Lab-only tooling (not part of the product): local `docker-registry` on 127.0.0.1:5000, `skopeo` signing with a lab key pair and a second "other" key, images assembled without a container engine (`scripts/lab_guest/mkimg.py`, `labprep.sh`), a signed local apt repo (`mkrepo.sh`), agent upgrade script `pushagent.sh`. ## Known gaps / next
- Awaiting real VMs: cloud-init on a Proxmox VM (NoCloud ISO/snippets), guest-agent read of the fingerprints, timesyncd, ssh host keys, Debian 12.
- Wire `agentcall.execute` into the deployment engine's executor and add the runbooks to the ICS risk table (suggested: `pull_verified`, `status`, `facts` low; `deploy_unit`, `remove_unit`, `pkg.install_pinned` normal; `remove_unit` with `purge_volumes` high). Pulls and apt can take minutes: the worker deadline must be raised for them (`agentcall.execute(deadline=600)` does; one agent exec at a time still applies).
- Podman secrets: `deploy_unit` can reference an existing secret by name; **creating** one on the node is Planned (needs a sealed channel for the value).
- The embedded, hash-verified agent bundle should be replaced by a signed `ou-agent` package once the OU repo exists (ADR-0008).
