# CLAUDE MASTER PROMPT — OFFICE UNBOUND WINDOWS DESKTOP APPLICATION

## OBJECTIVE
Plan, design, and begin building **Office Unbound Desktop**, a unified Windows application for the Office Unbound platform. Repository: https://github.com/agit8or1/office-unbound
The application should offer functionality comparable to the combined Microsoft OneDrive and Teams desktop experience, with integrated access to files, chat, meetings, calendar, email, contacts, and documents.
**WINDOWS FIRST.** Build for Windows 10/11 x64 initially. Design the architecture for future macOS, Linux, Android, and iOS applications, but do not begin developing those clients yet.
This is authorization to proceed beyond planning and begin Windows implementation. It supersedes previous *planning-only* or *separate approval required* restrictions for the Windows desktop client. It does not authorize deploying to production, modifying existing production installations, or beginning desktop OS authentication/MDM development.

## 1. EXISTING INFRASTRUCTURE — REUSE IT
Before coding, inspect the repository and existing documentation, particularly: `CLAUDE.md`, `ROADMAP.md`, `docs/ARCHITECTURE.md`, `docs/requirements/desktop-connector.md`, `docs/requirements/onedrive-and-file-sharing.md`, `docs/requirements/office-unbound-connect.md`, existing identity, portal, OpenCloud, and collaboration code.
Office Unbound already uses or is developing: Keycloak / OpenLDAP for identity and authentication; OpenCloud for files, shares, and WebDAV; OpenCloud Desktop sync engine; Synapse / Matrix Authentication Service / Element for chat; Jitsi for meetings; Gromox for mail, calendars, and contacts; Collabora for document editing; Infrastructure Control Server (ICS) and tenant administration.
Verify which services are actually working before integration. Do not assume that a roadmap entry means a feature exists.
**Do not replace these backend services or create redundant infrastructure.** The desktop client must communicate with the existing Office Unbound deployment through its established HTTPS gateway and public subdomains. One public IP must remain sufficient.

## 2. APPLICATION ARCHITECTURE
Preferred technology: Tauri 2 desktop application; Rust for native Windows functions and background operations; Vue 3 / TypeScript or the existing frontend framework, whichever maximizes component reuse; native Windows notifications and system tray; SQLite for local non-secret state where appropriate; Windows Credential Manager / DPAPI for credentials; reusable service clients and platform abstractions. Validate this approach against Qt and other suitable FOSS choices before finalizing.
Two independently functioning components: **A. Background service / sync engine** — synchronization, reconnecting, transfer queues, local notifications, scheduled operations; continues when the main window is closed; prefer a per-user background process unless an actual Windows service is necessary. **B. Desktop application** — files, conversations, meetings, notifications, account settings, diagnostics. The background component must be able to run independently of the GUI. Avoid unnecessary CPU, RAM, disk usage, background polling, and duplicate processes.

## 3. SINGLE SIGN-ON AND FIRST-RUN EXPERIENCE
A new user should be able to: 1. Download Office Unbound Desktop. 2. Install it using a standard Windows installer. 3. Enter their company email address or Office Unbound server URL. 4. Discover or securely select the correct deployment. 5. Authenticate through Keycloak in the system browser. 6. Complete MFA if required. 7. Have their authorized files, chat, and services automatically configured.
No manual WebDAV configuration, Matrix server configuration, API tokens, or complicated setup instructions. Use OIDC Authorization Code + PKCE, secure redirect handling, token refresh, and native Windows credential protection. Support multiple organizations/accounts with strict isolation. Revoking a device or user must invalidate applicable sessions and prevent new server access. Do not promise remote deletion of previously downloaded data unless separately implemented and verified. Never store user passwords in application configuration files.

## 4. FILE SYNCHRONIZATION — ONEDRIVE-LIKE
PRIMARY FEATURE. Reuse the existing OpenCloud synchronization engine wherever practical.
Requirements: automatic bidirectional sync; selectable local folders; selective sync by folder; personal storage; shared-with-me folders; team and department libraries where supported; offline access to downloaded files; automatic sync after reconnection; background upload/download queue; file and folder change detection; rename and move detection; conflict detection and safe conflict copies; version history and restore; pause/resume; bandwidth and resource limits; transfer progress, speed, queue, and errors; notifications for completed transfers and failures; Windows Explorer integration and sync status icons; context-menu actions such as share, copy link, and view online.
Evaluate the Windows Cloud Files API for true Files On-Demand (placeholders, hydration, dehydration, available-offline status). Do not claim Files On-Demand works until it has been proven on actual Windows systems.
**DATA SAFETY IS CRITICAL.** A failed connection, expired credential, broken mount, unavailable server, or corrupted local state must never cause accidental mass deletion. Implement safeguards for unexpected bulk deletion, overwrite, or replacement. Handle: Windows path length and invalid characters; case-insensitive filename conflicts; NTFS permissions and timestamps; symlinks, junctions, filesystem loops; partial uploads/downloads; large files and interrupted transfers; simultaneous editing on multiple computers; file locking where supported; server-side permission changes. Never silently overwrite conflicting user data.

## 5. OPTIONAL HTTPS MAPPED DRIVE
Support a mapped drive option comparable to a network share, using the existing desktop connector requirements. Evaluate rclone, WinFsp, OpenCloud WebDAV over HTTPS, device-specific OIDC credentials. User chooses **Sync folder** (downloads selected files locally and syncs) or **Mapped drive** (presents permitted remote files in Explorer without a full local copy). Optional default drive letter `O:`, configurable, detecting existing mappings. Do not expose SMB or NFS over the public internet. Safely report offline write failures rather than imply uncommitted data was saved. Do not create sync loops between mounted drives and local sync folders.

## 6. CHAT — TEAMS-LIKE EXPERIENCE
Integrate the existing Matrix/Synapse/Element infrastructure; users should NOT need to install and configure Element separately. Provide: direct messages; group conversations; teams/rooms/channels; history and search; file and image attachments; drag-and-drop sharing; emoji and reactions; threaded replies where supported; editing and deletion; read/unread; mentions and notifications; presence; desktop notifications; muting; favorites and pinning; user and group directory lookup. Support standard Matrix functionality and permissions. Evaluate embedding/reusing Element versus a native UI on an appropriate Matrix SDK; choose the most maintainable and secure option that does not create a separate chat ecosystem. Same Office Unbound identity; verify how MAS and Keycloak sessions will be shared or coordinated. Maintain encrypted-room compatibility; never weaken Matrix encryption or authentication. Chat must work independently of file sync when either is disabled by policy or configuration.

## 7. MEETINGS, CALLS, AND NOTIFICATIONS
Integrate the existing Jitsi stack when backend functionality is available: start a meeting, join from chat, invitations and links, audio/video, screen sharing, device selection, mute/unmute, camera controls, meeting notifications, calendar-linked meetings. Initially, launching authenticated meetings in the system browser is acceptable. Move meetings in-app only after verifying auth, camera/mic permissions, screen sharing, and stability. Integrate the existing Asterisk telephony platform later via a separate optional module; do not rebuild the PBX. Do not describe meeting features as functional until verified.

## 8. UNIFIED APPLICATION INTERFACE
Polished, compact, intuitive; the usability of OneDrive and Teams together without duplicating Microsoft's appearance. Use Office Unbound's own visual identity aligned with the redesigned portal and admin interfaces. Suggested navigation: Home, Files, Chat, Meetings, Calendar, Mail, Contacts, Notifications, Settings. Compact, collapsible; contextual actions over permanent menu items. Home: recent files, sync activity and health, unread conversations, upcoming meetings, relevant notifications, quick actions. Thoughtful colors, spacing, icons, typography, cards. Requirements: light and dark themes; native Windows window behavior; high-DPI; resizable responsive layout; accessible keyboard navigation; clear connection and sync status; no excessive blank space; no giant navigation menus; no unnecessary decorative dashboards; no generic-looking AI-generated UI. Reuse existing design tokens and components. Functional pages, not empty mockups.

## 9. MAIL, CALENDAR, CONTACTS, DOCUMENTS
Modular architecture. Mail: inbox, compose, desktop notifications, attach local or cloud files, shared mailboxes. Calendar: day/week/month views, upcoming events, invitations, shared calendars, reminders. Contacts: corporate directory, search, details, start chat/call/email. Documents: browse and open, open in Office Unbound Docs, offer locally installed compatible office apps, safe save-back via sync or mapped drive. Initially portal-backed views or authenticated browser launches are acceptable; build native only when meaningfully better. Do not create a second mail backend, calendar store, document engine, or contact database.

## 10. WINDOWS INTEGRATION
System tray with useful menu; optional start at login; start minimized; native toasts; Explorer context menus; Explorer status indicators where feasible; open local sync folder; open cloud files in browser; file association/deep-link evaluation; show sync activity; auto reconnect; optional desktop shortcuts; uninstall and cleanup. Standard Windows installation and security practices. Closing the main window must not stop background sync; provide clear controls to fully exit.

## 11. MSP AND BUSINESS ADMINISTRATION
Support or plan: centrally defined settings; approved sync directories; bandwidth policies; disable sync or offline caching by policy; enable/disable modules; device enrollment and inventory; device-specific access revocation; version reporting; stable and prerelease channels; update policies; company branding where permitted; multi-tenant isolation; silent install and mass deployment; GPO/Intune-compatible configuration packages. The ICS must not become an unrestricted remote-control mechanism for desktops; keep device management separate from infrastructure control with narrowly scoped APIs. Policies enforced by the server where applicable, not merely hidden in the UI.

## 12. SECURITY REQUIREMENTS
Mandatory: TLS validation; no disabled certificate checks; no hardcoded credentials; no auth bypass; no global admin tokens on endpoints; strict tenant isolation; Windows-protected token storage; minimal permissions; strong input validation; secure external URL and deep-link handling; no untrusted command execution; no unrestricted local service API; safe plugin and update boundaries; sanitized logs; no secret-bearing support bundles; signed release manifests and verified updates; dependency vulnerability scanning; SBOM generation; FOSS licence compliance. Strict CSP and safe native/webview IPC. Check dependencies before incorporating code. Security testing must include token theft exposure, authorization boundaries, unsafe IPC, local privilege escalation, and cross-tenant data access. No telemetry or external reporting by default.

## 13. INSTALLER AND UPDATES
Reproducible Windows installer and upgrade path: Windows 10/11 x64; MSI and/or setup exe; per-user install where possible; enterprise unattended options; safe upgrades preserving data and config; rollback planning; clear error reporting; no bundled extras. Use the existing release strategy; stable, alpha, prerelease channels clearly separated. Trustworthy signed-update mechanism; never bypass signature checks. Third-party cost must remain ZERO: unsigned dev/alpha installers are acceptable with explicit Windows trust warnings; do not buy code-signing certs or paid services without approval; never claim installers are officially signed when they are not.

## 14. DEVELOPMENT PHASES
Continue implementing completed phases without waiting for unnecessary approval.
Phase 0 — Discovery and design: architecture document; module/component diagram; dependency and licence review; data flow and auth design; UI layout/design spec; milestones; risks and acceptance tests; what exists, what's reusable, what's new.
Phase 1 — Working Windows foundation: app shell; tray; settings; login/logout; Keycloak auth; account/server config; secure credential handling; background process; basic installer; real connection to the Office Unbound test stack. Don't stop at screenshots or placeholders.
Phase 2 — Files: OpenCloud auth; two-way sync using the existing engine; sync folder config; status and activity; offline/reconnect; conflicts; selective sync; basic Explorer integration. Validate file integrity with real tests.
Phase 3 — Chat: Matrix auth; conversation list; DM/group messaging; attachments; notifications; unread counts; search and presence.
Phase 4 — Mapped drive and enhanced files: HTTPS mapped drive; personal and shared spaces; reconnect and recovery; Explorer interaction; Files On-Demand if verified; performance and UI.
Phase 5 — Meetings and productivity: Jitsi, calendar, mail, contacts, document opening/editing, reusing existing apps and APIs.
Phase 6 — Business readiness: device enrollment/revocation; tenant admin; MSP deployment options; updates; diagnostics; installer hardening; security review; alpha release prep.
Phase 7 — Future platforms (ROADMAP ONLY): macOS, Linux, Android, iOS clients; mobile files, chat, meetings, enrollment, selective wipe. Keep reusable protocol code separate from platform integrations. The Entra-like desktop OS login feature is a separate future project; don't confuse it with signing in to the app.

## 15. TESTING AND ACCEPTANCE
Automated and reproducible integration tests. At minimum: 1. fresh install and first-run login; 2. MFA and token renewal; 3. small and large file upload/download; 4. offline edits and reconnect; 5. conflicting edits from two clients; 6. deletion safeguards and version recovery; 7. shared-folder permissions; 8. chat send/receive and notifications; 9. reconnect after Windows restart; 10. device/session revocation; 11. installer upgrade and uninstall; 12. no credential leakage in logs or settings; 13. acceptable idle memory/CPU; 14. isolation between organizations; 15. files intact after app or network failure. Disposable test data. Do not report Windows functionality as tested because Linux unit tests, compilation, or headless tests passed. If no Windows environment is available, build and test everything possible, identify the missing real-Windows validation, and do not declare the feature working.

## 16. DEVELOPMENT RULES
FOSS-compatible; zero mandatory licensing/subscription fees; no artificial user/device limits; reuse existing backend functionality; avoid unnecessary infrastructure; minimise dependencies; do not interrupt existing alpha users or deployments; feature branch; no untested changes to production; never alter live identity realms or credentials without authorization; document API changes and migrations; preserve compatibility; update ROADMAP.md with evidence-based status; do not mark untested features available; reuse existing build/CI; token-efficient (targeted reads, no repeated full scans, concise summaries); don't rebuild what a suitable upstream FOSS component already provides. Commit completed, tested milestones independently with meaningful messages.

## 17. WHAT I EXPECT FROM YOU
Do not just produce a plan and stop. Evaluate the repo, deliver the architecture and plan, then immediately begin Phase 1 and continue into later Windows phases as dependencies and tests permit. Prioritise a REAL, installable, functional Windows application over speculative features and mockups. After each milestone report: what was implemented; what works and was tested; what remains; security/compatibility concerns; tests passed/failed; commits; next priority. Provide a Windows installer artifact when the environment supports a verified build, or identify exactly what build infrastructure is missing. Do not claim an installable Windows application if no installer was built.
FINAL GOAL: a business user downloads ONE Office Unbound Windows application, signs in ONE time, and can immediately use their permitted cloud files, synchronise folders, chat with coworkers, receive notifications, join meetings, and access the rest of Office Unbound through a clean, unified interface — practical, reliable, secure, extremely easy to use.
