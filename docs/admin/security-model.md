# Security model

Label: the controls below are **Tested** (automated tests, security reviews with published findings). There has been **no external penetration test** and no production hardening review. This page explains [ADR-0002](../adr/0002-ics-security-model.md) in plain language and lists the actions that only the owner can do.
Technical detail and the enforcement table: [Security (technical)](security.md). Open findings are published, not hidden: [security-review-5-2026-11-15.md](../status/security-review-5-2026-11-15.md) and the earlier reviews in `docs/status/`. Reporting a vulnerability: [SECURITY.md](../../SECURITY.md).

## 1. The model in ten sentences
1. **People log in to the ICS with local accounts**, a password and a mandatory authenticator code (TOTP). They do not use any customer's identity system, so a customer problem cannot lock you out and a customer admin cannot become an ICS admin.
2. Roles are viewer, operator, approver, admin. **Nobody can approve their own request.**
3. There is **no free-form command box**. The ICS can only do things from a closed list of typed actions with validated fields. No SSH-with-sudo, no terminal proxy, no guest-agent exec, no Docker socket is exposed through the ICS.
4. Every change goes: **plan, approval, one-time job, audit**. Risky changes need two different approvers. The approval is bound to the exact parameters, so it cannot be reused for something else.
5. The **audit log** is append-only and hash-chained, with a per-entry signature using a key that is not in the database. The application's database role cannot update or delete audit rows or approvals. `ics.cli verify-chain` proves nothing was altered.
6. **Proxmox access uses two separate, limited identities** (never `root@pam`, never a token without privilege separation): a read-only inventory token and an optional provisioning token limited to one pool, storage and bridge. The ICS adds its own limits on top (allowed nodes, its own VM protected, only guests it tagged).
7. **TLS is always verified**, against a CA you give it or a fingerprint you pin. There is no trust-on-first-use and no "skip verification".
8. **Stored secrets are encrypted** (AES-256-GCM) with a key in a root-only file. If the key or the data does not match, it fails; there is no plaintext fallback. Secrets are never put in logs, audit entries, plans or API answers.
9. **Node agents** run as an unprivileged user and accept only signed, single-use, time-limited requests for fixed runbooks on a root-owned allow-list.
10. **The console is reachable only from your admin networks** (nginx and a firewall table generated by the installer).

## 2. What this model does not protect against
- **Root on the ICS host can do anything**, including create accounts and read keys with `ics.cli`. That is deliberate (it is the break-glass path) and it is audited as actor `cli`, but it cannot be prevented. Limit who has root there.
- If the running ICS application is compromised, the attacker holds its database role, the vault key and the audit key: they can read stored secrets and append valid audit entries, but cannot alter or delete earlier audit rows or approvals.
- Tail truncation of the audit log by the database owner is not detectable from the database alone (off-host export of a signed head is **Planned**).
- Jobs run inside the ICS process (a separate privileged executor is **Planned**).

## 3. Owner actions (only the owner can do these)
These are open items from the reviews. They are listed here because the software cannot do them for you.
| # | Action | Why | Where it is tracked |
|---|---|---|---|
| 1 | **Remove the blanket passwordless sudo (`NOPASSWD: ALL`) from the build/operator account on the ICS and build host.** Keep only the single narrow rule for the release signer | While it exists, anyone who gets that account becomes root, can read the release-signing passphrase and key, and can sign a release with no second person. Removing it alone is not enough: the promotion gates must also be attested by someone other than the same caller | [security-review-5-2026-11-15.md](../status/security-review-5-2026-11-15.md) finding H2; [package-pipeline-results.md](../status/package-pipeline-results.md) |
| 2 | **Copy the release key's offline revocation certificate to offline media and keep it safe**, then remove the copy on the host | If the release signing key is ever stolen, only this certificate lets you declare it revoked. It is generated on the host at `/root/ou-release-revocation-<fingerprint>.asc` | package-pipeline-results.md, "Key ceremony" |
| 3 | **Rotate the Proxmox token that was pasted into chat** and rotate periodically | A secret that has been exposed must be replaced. Rotation is the manual `pveum` procedure; the ICS rotation actions have only been run against a simulator | [Connecting Proxmox](connecting-proxmox.md#7-token-rotation) |
| 4 | **Keep an offline, sealed copy of `vault.key`** (and `audit.key`, `ics-signing.key`) | Backups restore, but without `vault.key` every stored secret is lost; without `audit.key` the audit chain cannot be verified | [ICS recovery and warm standby](ics-recovery-and-standby.md) |
| 5 | **Store the backup product's offline recovery key** (printed or on offline media, fingerprint verified, file shredded) | Lets you read the backups even if the ICS vault is lost | [Backup and restore](backup-and-restore.md) |
| 6 | **Move release signing offline or to a hardware key** and define key rotation | The lab key sits on the build host | package-pipeline-results.md; [upgrades.md](upgrades.md) |
| 7 | **Do not run the lab demo scripts on a real controller** and do not leave demo accounts | The scripts create throwaway users and checks | [Installing the ICS](installing-the-ics.md) |
If you cannot do an item, write down the decision and the date in `docs/status/host-changes.md`.

## 4. Rules for engineers
- Never paste a secret into chat or a ticket. If you did, rotate it.
- Never widen a Proxmox allow-list to make a failing plan pass; ask the owner of that infrastructure.
- Verify certificate fingerprints on the machine's own console, not over the network path the ICS will use.
- High-risk plans: read what you approve. The plan page shows the exact parameters.
