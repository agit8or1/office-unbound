# Known limitations (0.13 "Meridian", alpha)

What not to promise yet. Updated 2026-11-24 (0.13); each line says where it is tracked. Install steps: [Alpha install guide](alpha-install.md).

## Scope of what was proven
- **One reference installation.** Everything below "works" means: run on one ICS host, one Proxmox VE node (pve06) and one public IP, with
  one deployment at a time (officeunbound .. officeunbound7). Multi-node placement, several customers side by side on real Proxmox and
  network isolation between them (SDN) are not proven on real infrastructure (isolation is tested in the lab: [tenant-isolation-results.md](../status/tenant-isolation-results.md)).
- **No production data.** 0.x releases may change data formats and the deployment layout.

## Installing
- **Release artifacts are not downloadable yet.** The golden VM image and the `ou-*` packages are built and signed on the reference host
  (release signer, test runner and build machines). An outside installation can install the ICS from the tag but needs the project's help to
  get signed artifacts ([alpha-install.md](alpha-install.md) step 4). A public signed download is **Planned**.
- **The public entry is configured by hand.** The ICS host routes each public name to the deployment's gateway VM through nginx, and that map is
  edited by hand, again after every rebuild (the gateway gets a new address). Generated by the ICS: **Planned** (ADR-0018 G1, GitHub #23).
- `--tls-cert/--tls-key`, IPv6 and installation without internet access are not tested ([installing-the-ics.md](installing-the-ics.md)).

## Deployments
- **In-place upgrades** (0.12.0, implementing): `deployment.change` updates the node agent, adds components to existing VMs and reconfigures
  the components that depend on them, on the VMs a deployment already has (no new image, accounts, mail and files stay). The first
  real change (officeunbound8) has not completed yet: five attempts stopped at the first VM's agent update, each on a gap the test
  doubles did not have (fixed in 0.12.1, 0.13.0, 0.13.1, 0.13.2 and 0.13.3); the sixth updated that agent and stopped at the chat install
  (image pull order, fixed in 0.13.4), the seventh at chat's first unit (mounts under /etc, fixed in 0.13.5), the eighth installed chat and
  upgraded Files and Office, then stopped at chat's health check (probes the agent could not run, fixed in 0.13.6). Every stop left the
  running apps working; the last three left chat's packages, databases, configuration and services on the files VM
  ([host-changes.md](../status/host-changes.md)). A deployment whose agent is older than 0.10.1 first gets the agent upgrade (one
  change), then the rest. Not yet in place: removing a component from a VM, moving one to another VM, a new golden image for existing VMs
  (the OS is patched by package updates, not replaced), and runbook unit files changed by a newer agent (`/etc/systemd/system` copies
  written at first boot take precedence). Data disks of components added later are attached but, as at creation, not mounted.
- Branding/skin changes (0.13.1) reach a running deployment with its next change: the plan records a digest of the brand sources on
  identity, files, groupware and chat, and a different digest reconfigures those in place (no automatic push; each change is approved).
- **Certificates:** Let's Encrypt allows 5 certificates for the same set of names per week. Since 0.9.4 the ICS keeps an encrypted copy of the
  gateway's certificate and gives it back to a rebuilt gateway; verified live on 2026-11-23 (officeunbound7 rebuilt as officeunbound8: same
  certificate restored in 17 s, no new order; GitHub #24). Certificates are reused only while valid for more than 30 days. DNS-01, wildcard certificates and DNS automation are **Planned** (GitHub #25, #26).
- **Account self-service** (0.11.0): people edit their name, display name, phone and mobile and change their password from the portal
  only on deployments built with node agent 0.10.0 or later; older ones keep a read-only directory. There is no "forgot password" e-mail
  yet: an administrator creates a one-time link.
- **Chat** (0.11.0) is deployed by the ICS when the layout includes it; its media and configuration are not backed up yet, Matrix ids are
  `@user:matrix.<domain>`, federation is off, no mobile app is tested.
- **Not deployed by the ICS:** meetings and telephony (lab prototypes only; since 0.14 refused in plans unless the host owner turns them on with `ICS_EXPERIMENTAL`, [installing-the-ics.md](installing-the-ics.md)), anti-spam and antivirus (rspamd, ClamAV: **Planned**),
  mail archiving (**Planned**).
- **Internet mail** (MX delivery in and out, SPF/DKIM/DMARC) is not verified end to end. On a deployment, webmail, ActiveSync and
  CalDAV/CardDAV answer and pass their health checks ([groupware-deploy-results.md](../status/groupware-deploy-results.md)).

## Look and design (0.13 redesign)
- **One design, three upstream apps.** The portal is Office Unbound's own; webmail/calendar/contacts (grommunio-web), Files (OpenCloud),
  sign-in (Keycloak) and chat (Element) are restyled only through their supported theming hooks (colours, borders, type), never their
  layouts, dialogs or settings pages ([design-system.md](../design/design-system.md)). Upstream wording and layout show through there.
- **Light/dark is per app.** The portal's Appearance switch does not reach the apps; webmail, Files and chat each keep their own choice.
  Until a user chooses, Files and (from webmail 5.2-ou5) webmail follow the browser like the portal; chat always opens light, its dark
  theme is under Settings, Appearance. Seen live on officeunbound8 (2026-11-25); a person who already chose
  Light or Dark in webmail keeps that choice (choose System to follow the browser).
- **Adding chat to a deployment with a public certificate needs the certificate issued again** (gateway.certificates.issue, staging then
  production): until then chat, matrix and mas are served with the deployment certificate and browsers warn. The in-place change does not
  do it by itself (officeunbound8, issued again by hand 2026-11-25).
- **The dashboard shows only what it can read.** Inbox, unread counts, the next meeting and mail/calendar reminders need a mailbox data
  source that is not verified yet: those widgets offer working actions instead of data. Notifications in the bell are the Files ones only.
  No tasks or notes app exists, so none is shown.
- Chat's dark accent: white text on its accent buttons is 3:1 (large-text level, not 4.5:1), the accent as text on menus about 4.3:1.

## Apps and clients
- Webmail is grommunio-web with the Office Unbound look; the upstream name can still appear where the skin does not reach (texts inside
  dialogs are not rewritten).
- New Outlook for Windows and Outlook mobile cannot use MAPI/EWS against a non-Microsoft server (IMAP/SMTP only). Classic Outlook and Outlook for
  Mac are the targets, but **no real Outlook, phone or Apple client has been tested**; Thunderbird and Evolution were tested automatically
  ([client-compat-results.md](../status/client-compat-results.md)).
- Device onboarding profiles are unsigned and untested on real devices.
- Mail migration: the assessment has never run against a real Microsoft 365 or Google tenant, and the IMAP mover is lab-proven for one
  mailbox, with no calendar, contact or file migration ([migration.md](migration.md)).

## Operations
- The reference installation runs with one administrator (`ICS_APPROVAL_MODE=single_admin`, [ADR-0017](../adr/0017-single-admin-approval-mode.md)); the
  two-person rule is covered by automated tests.
- ICS controller backups (`ics-backup.sh`) are taken by hand before each change; they are not yet scheduled, encrypted or copied off the host
  ([backup-and-restore.md](backup-and-restore.md)). No HA controller; a warm standby with operator-triggered promotion exists and is lab-proven
  ([ics-recovery-and-standby.md](ics-recovery-and-standby.md)).
- Pushover and SMS alert channels cannot be enabled (ADR-0007); the webhook channel is tested locally only.
- No mailbox purge or export action; revocation gaps are listed in [users-and-access.md](users-and-access.md).
- **ActiveSync remote wipe is experimental and off** (since 0.14: refused unless `ICS_EXPERIMENTAL=remote-wipe`). **It is not device management.** `idm.user.disable` with `wipe_devices` asks **every** ActiveSync device of the user for a
  full remote wipe; depending on the phone's mail app that can erase the whole phone, including a personally owned one. It was tested only with a
  scripted client (no real phone), the device's acknowledgement is not proof of erasure, an offline device never receives it, and in
  `single_admin` mode the administrator approves it alone. Use it only on company-owned devices you intend to erase
  ([lifecycle-gaps-results.md](../status/lifecycle-gaps-results.md); planned replacement: [mobile-remote-wipe-security.md](../requirements/mobile-remote-wipe-security.md)).
