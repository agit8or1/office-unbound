## What is enforced where
| Control | Enforced by |
|---|---|
| Closed action catalog; plan hash bound to approvals; two approvers for high risk; requester never approves own plan | ICS app + insert-only `plan_approvals` table (the `ics_app` DB role has no UPDATE/DELETE) |
| Audit: SHA-256 hash chain + per-row HMAC (`audit.key`, never in the DB); trigger forces `prev_hash`, sequence, MAC | ICS + Postgres trigger |
| Passwords argon2id, mandatory TOTP, throttled login (per user+IP, exponential), session cookie `__Host-`, CSRF header, strict CSP | ICS |
| TLS always verified (CA bundle or SHA-256 pin); no trust-on-first-use; SSRF guard on destinations (loopback/link-local/metadata refused, resolved IP pinned for checks) | ICS |
| Node agent: Ed25519-signed single-use requests, replay journal, allowlist from a root-owned file, polkit limits systemd actions to listed units, no shell | agent + host polkit |
| Service hardening (NoNewPrivileges, ProtectSystem=strict, empty capability set, syscall filter) | systemd units in `ics/deploy/` |
| Console exposure limited to admin ranges | nginx allow/deny + nftables (`ics-admin-fw`), generated by `bootstrap.sh` (not attacked from a denied address in the lab) |
| Proxmox scope: pool/storage/network/node allowlists (nodes deny by default), tagged-guest ownership, the ICS's own VM protected | ICS provider before any API call; refusals confirmed on a real cluster ([connecting-proxmox.md](connecting-proxmox.md)) |

## Secrets handling
- Stored secrets are AES-256-GCM encrypted with `vault.key`; AAD binds each secret to its endpoint/check/stack config, so re-pointing it voids it. Decryption failure is a hard error.
- Secrets never appear in logs, audit details, plans, job results or API responses (asserted by tests and scans in the lab runs).
- Key files are root-owned `root:ics 0640`, regular files only; `ics-migrate.env` (DB owner) is root 0600 and unreadable by the app. Never paste secrets in chat.
- Compromise of the running app yields `ics_app`, vault and audit keys: it can read secrets and append valid audit entries, but cannot alter or delete audit rows or approvals.

## Credential vault: envelope encryption and master-key re-wrap
Evidence: [credential-vault.md](../status/credential-vault.md) (tests `ics/tests/test_vault_m.py`, `test_vault_audit.py`; mock provider, never a real one).
- Provider credentials (Proxmox tokens and temporary admin credentials) are stored in the `credentials` table with **envelope encryption**: a random 256-bit data key per credential encrypts the secret with AES-256-GCM, and the master key (the same `vault.key` file as before) wraps the data key. Both layers are bound to `credential:<id>:<provider>:<customer>` as authenticated data, so moving or editing a row makes it undecryptable.
- Only the service's secret getter returns plaintext, and it refuses revoked, expired, invalid and retired credentials. Every use is audited (`credential.use`; inventory use at most every 5 minutes per credential). Temporary admin credentials live at most 15 minutes and are destroyed when the job ends, is rejected or expires.
- Legacy per-endpoint secrets are moved into the vault by `cd /opt/office-unbound/ics && sudo -u ics .venv/bin/python -m ics.cli migrate-credentials` (idempotent; also run at application start).
- **Rotate the master key** with `ics.cli rewrap-master`: one all-or-nothing database transaction that re-wraps data keys and re-encrypts every other vault secret (TOTP seeds, check, alert channel and IdM secrets, pending plan secrets). Steps from credential-vault.md:
  1. Create the new key: `umask 077; head -c 32 /dev/urandom > NEW; chown root:ics NEW; chmod 0640 NEW`.
  2. Stop jobs if possible; as the `ics` user run `python -m ics.cli rewrap-master --new-key-file NEW` (it needs the current key from the settings plus the new one).
  3. Point `ICS_VAULT_KEY_FILE` at `NEW`, keep the old file offline until verified, restart `ics`.
  4. Check `GET /credentials` and run one `credential.test`. The audit event `vault.master_key_rewrapped` records key ids, not keys.
  Tested: success, and failure leaves data unchanged (test suite only; not drilled on a lab controller). A backup taken before the rewrap needs the old key, so take a new backup afterwards.
- Security review 3 (1 High, 5 Medium, 8 Low) fixes are merged with regression tests: [security-review-3-2026-11-15.md](../status/security-review-3-2026-11-15.md), "Remediation".

## Release signing, promotion and the build user (security review 5: H1, H2)
Evidence: [security-review-5-2026-11-15.md](../status/security-review-5-2026-11-15.md) "Remediation"; tests `ics/tests/test_release_signer.py`, `ics/tests/test_release_promote.py`.

**What the code now enforces**
- `ou-release-sign sign <suite>` no longer signs what the caller wrote. It parses every index listed in `Release` (`Packages`, `Packages.gz`, `Packages.xz`, `Sources*`), checks size and every hash section, refuses unlisted extra files and non-allowlisted paths, refuses compressed variants that differ from the plain index, requires every stanza to point into `pool/<suite>/` with a sha256 in that suite's ledger, and then **rebuilds** the `Release` itself (`Suite`/`Codename` = its own argument, `Date`, `Valid-Until`).
- Packages enter `staging`/`stable` only through the ICS: the typed action `release.promote` (admin requests; `dev>staging` needs one approver, `staging>stable` is high risk = two approvers, never the requester) carries the exact package set (file, name, version, sha256) and the test evidence (hash of the test runner's attestation per `.deb`). The executor signs a **promotion manifest** with the ICS signing key and passes it to `repo.sh promote-manifest`; `ou-release-sign promote` verifies the signature (key in the root-owned `/var/lib/ou-release/trust/ics-promotion.pub`), expiry, approver count, requester exclusion, single use (nonce), the exact file set and the evidence.
- Test records are no longer typed. `ou-test-attest` (user `ou-testrunner`, own key, public half in `trust/test-runner.pub`) signs "package sha256 X passed install-smoke, log sha256 Y" and refuses packages that were never admitted; `ou-release-sign record-test` accepts only such an attestation.
- Install/re-install the programs (idempotent, root): `sudo OU_ICS_PROMOTION_PUB=<file with the base64 raw ICS signing public key> bash blueprints/build/repo/install-signer.sh`. The ICS public key is `python -c "from ics import agentclient as a; print(a.pub_b64(a.load_signing_key('<ICS_SIGNING_KEY_FILE>').public_key()))"` (run as a user that can read the key). Set `ICS_RELEASE_PROMOTE_CMD="/path/to/blueprints/build/repo/repo.sh promote-manifest"` in the ICS environment.

**What code cannot fix: `administrator` is root-equivalent (OWNER ACTION).** `/etc/sudoers.d/90-cloud-init-users` (`administrator ALL=(ALL) NOPASSWD:ALL`) and `/etc/sudoers.d/90-claude-administrator` (`administrator ALL=(ALL:ALL) NOPASSWD: ALL`) let any code running as `administrator` read `/var/lib/ou-release/passphrase` and the key, replace `/usr/local/sbin/ou-release-sign`, edit `trust/*.pub`, or add itself to any sudoers file. Every control above is separation of duties on paper until this is removed. **Superseded by a tested script:** `sudo ics/deploy/privsep/apply-privsep.sh` (dry run) / `--apply`, undo with `revert-privsep.sh`; the final rules, the lab workflow that remains and the key-separation evidence are in `docs/status/privilege-audit.md`. The manual procedure below is kept for reference only (its `systemd-run -M <machine> *` wildcard is replaced by argument-validated shims in the script).

The change (as root, from a console session that does not depend on those rules; keep a root shell open while doing it):

```
# 1. remove the two blanket rules (keep a backup outside /etc/sudoers.d)
install -d -m 0700 /root/sudoers-backup
mv /etc/sudoers.d/90-cloud-init-users /etc/sudoers.d/90-claude-administrator /root/sudoers-backup/
# 2. install the minimal rules the lab workflow still needs
cat > /etc/sudoers.d/ou-lab-workflow <<'EOF'
# signer and test runner: the ONLY programs that touch the release key / write attestations (fixed paths, fixed target users)
administrator ALL=(ou-release)    NOPASSWD: /usr/local/sbin/ou-release-sign
administrator ALL=(ou-testrunner) NOPASSWD: /usr/local/sbin/ou-test-attest run *
administrator ALL=(ou-imgsign)    NOPASSWD: /usr/local/sbin/ou-image-sign
# systemd-nspawn build/test/repo machines (names from blueprints/build/tools.env); no wildcard on the machine name
Cmnd_Alias OU_MACH = /usr/bin/machinectl clone ou-base-bookworm ou-pkg1, /usr/bin/machinectl clone ou-pkg-golden ou-pkg1, /usr/bin/machinectl clone ou-pkg1 ou-pkg-golden, \
    /usr/bin/machinectl clone ou-base-bookworm ou-pkgtest1, /usr/bin/machinectl clone ou-base-bookworm ou-repo1, \
    /usr/bin/machinectl start ou-pkg1, /usr/bin/machinectl start ou-pkgtest1, /usr/bin/machinectl start ou-repo1, \
    /usr/bin/machinectl terminate ou-pkg1, /usr/bin/machinectl terminate ou-pkgtest1, /usr/bin/machinectl poweroff ou-pkg1, \
    /usr/bin/machinectl remove ou-pkg1, /usr/bin/machinectl remove ou-pkgtest1, /usr/bin/machinectl show ou-repo1, \
    /usr/bin/systemctl set-property systemd-nspawn@ou-pkg1.service MemoryMax=*, /usr/bin/systemctl set-property systemd-nspawn@ou-pkgtest1.service MemoryMax=*, \
    /usr/bin/systemctl set-property systemd-nspawn@ou-repo1.service MemoryMax=*, \
    /usr/bin/tee /etc/systemd/nspawn/ou-pkg1.nspawn, /usr/bin/tee /etc/systemd/nspawn/ou-pkgtest1.nspawn, /usr/bin/tee /etc/systemd/nspawn/ou-repo1.nspawn, \
    /usr/bin/test -d /var/lib/machines/*
Cmnd_Alias OU_EXEC = /usr/bin/systemd-run -M ou-pkg1 *, /usr/bin/systemd-run -M ou-pkgtest1 *, /usr/bin/systemd-run -M ou-repo1 *
administrator ALL=(root) NOPASSWD: OU_MACH, OU_EXEC
EOF
chmod 0440 /etc/sudoers.d/ou-lab-workflow && visudo -cf /etc/sudoers.d/ou-lab-workflow
# 3. administrator keeps the password-protected group rule (%sudo ALL=(ALL:ALL) ALL) for everything else: interactive, with a password
```
Residual risk the owner must know: `systemd-run -M <machine> *` runs arbitrary commands as root **inside** the named container, and the nspawn machines are not a security boundary against a host-root equivalent (builder: `PrivateUsers=pick`, but `machinectl clone` of images and `/etc/systemd/nspawn/*.nspawn` creation by `tee` also need root). The builder/test steps therefore still amount to "can run code as root in the build containers", which is acceptable only because the containers hold no release key. Installs, `bootstrap.sh`, agent installs and service changes need a password-protected `sudo` (interactive) or a root session. Long term: run builds as a separate account (`ou-build`) on a separate host, with the signer on a third; production signing stays offline/HSM.

## Guest-bootstrap listener, shared rate limits, several workers (hardening, review 5 follow-up)

**Dedicated listener.** `bootstrap.sh --callback-listen IP[:PORT] --callback-allow-cidr CIDR [...]` installs `ics-bootstrap.service`: its own process and socket
(default `IP:8444`), its **own self-signed certificate** (`/etc/office-unbound/callback-tls/`, key root 0600, handed to the unit with `LoadCredential`), serving only
`POST /api/v1/guest-bootstrap/report` and `GET /healthz`. The installer sets `ICS_GUEST_CALLBACK_DEDICATED=true` (the console stops serving the route),
`ICS_GUEST_CALLBACK_URL` and `ICS_GUEST_CALLBACK_PIN_SHA256` (SHA-256 of the DER certificate = what guests pin through SMBIOS) in `ics.env`.
Without the flag the old behaviour stays (console serves the route): that is the transition setting; there is no automatic switch for existing installs.
Limits (server side, before any application code): 4 KiB body cap (Content-Length and chunked), 16 KiB header buffer, 10 s per request, 64 concurrent
connections, 5 s keep-alive, no HTTP/2, no WebSocket. The firewall (nftables table `inet ics_callback`, `ics-callback-fw.service`) lets only the
`--callback-allow-cidr` networks reach the port, at most 8 concurrent and 30 new connections/min per source. Re-issuing the certificate (expiry, IP change)
changes the pin: VMs that were provisioned but have not reported yet carry the old pin and fail closed; re-run the deployment step for them.

**Rate limits are shared.** Login throttling was already in PostgreSQL (`login_attempts`). The remaining in-process buckets (guest callback per source /
per bootstrap id / unknown ids, public approval links, identity enrollment) now use `rate_limits` (UNLOGGED token buckets, one atomic upsert per decision,
`ics/ics/ratelimit.py`), so the limits hold across any number of uvicorn workers or hosts sharing the database. A database error answers 5xx (fail closed).
`ics.service` runs `ICS_WORKERS=2` (override in `ics.env`, 1..16). The background worker (jobs, monitor, inventory, backups) runs in exactly one process,
chosen by a PostgreSQL advisory lock; if that process dies the supervisor restarts it and the lock is taken again.

**Proxmox exposure of the one-time SMBIOS secret.** See [hardening-results.md](../status/hardening-results.md). In short: the value is logged by Proxmox in the
cluster log and the node syslog on every config update (not in a task log: the ICS uses the synchronous PUT), and on a running VM the "clear" stays in the
`pending` section until the VM is stopped and started again. Grant `Sys.Syslog` on `/` only to Proxmox administrators, keep `ICS_GUEST_BOOTSTRAP_TTL_SECONDS`
short (300-900), and treat a consumed or expired secret as inert (single use, replay alarm).
## Security review 7 hardening: signer, test runner, fencing, tenancy (operator notes)
Evidence: [security-review-7-2026-11-16.md](../status/security-review-7-2026-11-16.md) "Remediation" (finding-by-finding with the tests).

**Release signer and channels.**
- `ou-release-sign` parses `Packages`/`Sources` with a strict deb822 parser (duplicate fields, stanzas, `Filename`s and `Package`+`Version`+`Architecture` are refused) and compares EVERY stanza with the control data, size and hashes it recorded when the file was admitted or promoted (`ledger/meta/<sha>.json`, `blobs/<sha>`). Free-text `Depends`/`Conflicts`/`Version` in an index no longer signs.
- **One key per channel.** `dev`, `staging` and `stable` are signed by three different keys (`FINGERPRINT-<suite>`). Stable keeps the lab key (`blueprints/build/keys/ou-release-lab.*`, now also `ou-release-stable.*`); first-contact guests (golden image) pin only that one. Dev and staging public keys: `blueprints/build/keys/ou-release-dev.pub.asc`, `...-staging.pub.asc`. A dev Release served as `stable` fails the signature check; it can no longer be installed with only a warning.
- Clients check the Suite/Codename themselves: the guest agent (`pkg.install_pinned`) runs apt with `Acquire::AllowReleaseInfoChange=false` and refuses a fetched `InRelease` whose `Suite`/`Codename` differ from the suite in its sources; the lab scripts under `blueprints/lab/upgrade/` and `blueprints/telephony/` pin the per-channel key and run the same check.
- **Re-install after pulling this change** (idempotent, root): `sudo OU_ICS_PROMOTION_PUB=<file> bash blueprints/build/repo/install-signer.sh`, then `blueprints/build/repo/repo.sh resign-all`. It creates the dev and staging keys, seeds the ledger metadata and blobs, installs `/usr/local/lib/ou-testrunner/{smoke-deb,nspawn-smoke}` and the sudoers rules (`/etc/sudoers.d/ou-release`, `/etc/sudoers.d/ou-testrunner`). Guests that pinned the old single key keep working on `stable`; any guest that follows `dev` or `staging` must be given that channel's key file.
- Offline copy of the two new revocation certificates: `/root/ou-release-revocation-<fingerprint>.asc` (root only).

**The test runner runs the tests (`ou-test-attest`).** The build user can only ASK: `sudo -u ou-testrunner /usr/local/sbin/ou-test-attest run <kind> <ref>`; there is no way to hand it a result, a name or a log hash. For a `.deb` (`deb-install-smoke`, ref = sha256) the runner fetches the admitted bytes from the signer's blob store, re-hashes them, installs the package in a throw-away `systemd-nspawn --volatile=overlay` container without network (`/usr/local/lib/ou-testrunner/nspawn-smoke`, base image `$OU_TESTRUNNER_BASE`, default `/var/lib/machines/ou-base-bookworm`), checks the install state, `dpkg --verify`, removal and purge, and signs what IT saw (attestation v2). Interface for other signers (stable, documented in the header of `blueprints/build/repo/ou-test-attest`): `run image-first-boot <absolute image path below /var/lib/ou-imgbuild/out>` runs the fixed program `/usr/local/lib/ou-testrunner/image-first-boot` (installed root-owned by the image signer's installer) on a private copy, and attests `{v:2, kind:"image-first-boot", name:"first-boot", sha256:<image>, result, log_sha256, at, run_id}`.
- Remove the blanket sudo rules (see above): while `administrator` has `NOPASSWD: ALL`, every gate is separation of duties on paper only. The sudoers drop-in for the lab workflow now reads `administrator ALL=(ou-testrunner) NOPASSWD: /usr/local/sbin/ou-test-attest run *`.
- Optional: a DEDICATED promotion key (`ICS_RELEASE_PROMOTION_KEY_FILE`, 32 raw bytes; public half to `trust/ics-promotion.pub`) so that compromising the ICS process's agent-signing key can not mint stable manifests. It is not part of the standby key bundle: copy it to a standby deliberately.

**Fencing.** A controller that is a standby, fenced, or whose database epoch differs from the epoch it started with does NOTHING: the worker claims no job (the claim re-reads `controller_state` `FOR SHARE` in the same transaction), the job/backup/monitor/inventory loops idle, no agent request or enrollment, Proxmox call, notification, package promotion or SSH bootstrap leaves the process (`ics/egress.py`), and every console/API mutation (including the guest callback) answers 503 with `X-OU-Role: fenced`. The state is sticky until the service is restarted. `fenced` can only become `primary` again through a promotion (migration `0012r7`). Promote as documented (stop the old primary or use `--fence-old-dsn-file`; the primary's `pg_hba` now admits the standby for that one purpose).
- Agent epoch file (`/var/lib/ou-agent/epoch.json` + `.bak`): if it exists but neither copy is readable the agent refuses everything (`epoch_state_corrupt`). Re-seed on the node console with a document the CURRENT controller signed: on the controller `python -m ics.cli epoch-attest --node <node-id> > doc.json`, on the node `ou-agent reseed-epoch doc.json`.
- Standby key bundle: the passphrase is shown on the terminal only, never written next to the bundle (use `OU_BUNDLE_PASSPHRASE_OUT=<file on another medium>` for unattended runs); `bootstrap.sh --standby-of` asks for it and wipes the bundle (and a passphrase file, if given) after a successful import.

**Fencing lease with a witness (partition-proof).** The check above reads the controller's own database, which a partitioned old primary still believes. With a witness configured the active controller may cause side effects ONLY while it holds a time-bounded grant (default T = 30 s, renewed every 5 s) signed by the witness: `lease_valid_until > monotonic_now` is checked before every job claim, job, provider/agent/notification/SSH call, enrollment and API mutation (`epoch.assert_active`, `egress.require`, `FenceGuard`). The grant is measured from BEFORE the request was sent, so delay only shortens it. If it is not renewed the controller fences itself; if the partition heals and nobody promoted it recovers on its own.
- Witness: `python -m ics.witness keygen --key-file /etc/office-unbound/witness.key` (prints the public key), then run `python -m ics.witness serve --key-file ... --controller-pubkey <primary's ICS signing public key> --state /var/lib/office-unbound/witness.json [--listen ip:8099 --cert --key]` on the STANDBY host (or a third host on the standby's side of any partition). Primary `ics.env`: `ICS_LEASE_WITNESS_URL`, `ICS_LEASE_WITNESS_PUBKEY` (+ optional `ICS_LEASE_WITNESS_TLS_FP`, `ICS_LEASE_SECONDS`, `ICS_LEASE_RENEW_SECONDS`). Without `ICS_LEASE_WITNESS_URL` the lease is OFF and single-controller installs behave as before.
- Promotion: on the promoting host set `ICS_WITNESS_STATE_FILE` (the witness state file; optional `ICS_WITNESS_MARGIN_SECONDS`, default 10). `ics-cli promote` first revokes the witness (it stops granting for the old epoch; the old primary is told `superseded` and fences itself for good) and WAITS until T + margin have passed since the last grant ever made, then bumps the epoch. Without that setting promotion is not lease-proven and prints a warning. Manual: `python -m ics.witness revoke --state ... --wait`.
- Trade-off: with a witness configured, a dead or unreachable standby makes the primary self-fence after T seconds. If the standby is known dead and you accept the split-brain risk, set `ICS_LEASE_STANDALONE_OVERRIDE=true` (recorded in the audit log as `controller.lease_standalone_override` at every start) and remove it when the standby is back.
- Defence in depth: agents still refuse a lower epoch. Not done: an epoch marker at the Proxmox provider (a compare-and-set on a sentinel in the pool comment); a fenced controller there is stopped only by the lease and the agents.

**Tenancy.** A plan's customer is derived by the server from every resource its parameters name (`ics/tenancy/resolve.py`): resources of two customers, or a `customer_id` that disagrees, are refused; a scoped operator who names another customer's object gets the same 404 as for a missing one. Maintenance windows without a check and alert notifications stay inside their own customer. A customer-scoped admin who invites an account creates it with the SAME scope (never all-customers) and at most their own role. `/api/v1/system` (exact version, commit, schema) is for all-customers admins only.

**Guest enrollment and the ARP witness.** The ICS now re-reads the neighbour entry before it connects, before the token is sent and after the agent answered, and refuses (and stops the VM) if the hardware address changed. This narrows, but cannot close, the window against an attacker on the same L2 segment who holds the bootstrap secret: enable the Proxmox firewall `macfilter` and `ipfilter` on every guest bridge/VM NIC (Datacenter/VM > Firewall > Options > "MAC filter" and "IP filter") so a guest cannot claim another MAC/IP. Without them, routed or shared-segment guest networks are only as trustworthy as the segment.

**Golden image import.** The release key and its pin come only from the ICS configuration (`ICS_GUEST_RELEASE_PUBKEY_FILE`, `ICS_GUEST_RELEASE_PIN_SHA256`); the per-OS downgrade floor lives in the database (`image_floor`, migration `0013r7`, monotonic) and is not lowered by deleting templates.

**Guest callback listener.** `ics/deploy/ics-callback.nginx.conf` is the reverse-proxy block for the dedicated listener (`ics-bootstrap.service`, `ICS_GUEST_CALLBACK_DEDICATED=true`). It stays optional (default off) until the owner has put the proxy in place.
