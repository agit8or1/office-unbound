# Changelog

All notable changes to Office Unbound are recorded here. The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/);
versioning follows [Semantic Versioning](https://semver.org/) as defined in [ADR-0011](docs/adr/0011-versioning-and-releases.md).
While the major version is 0 the project is pre-alpha: MINOR releases may contain breaking changes.

Every entry links to the document that holds its evidence (executed tests, lab results, review reports). An entry without
evidence is a plan, not a change (ADR-0000). Release 0.1.0 is a **lab pre-alpha**: everything below was demonstrated in an
isolated lab; nothing is production supported ([ROADMAP.md](ROADMAP.md)).

## [0.9.2] - 2026-11-22

- **Fixed: before public certificates, `mail.` and `autodiscover.` failed certificate checks through the gateway.** The gateway's deployment certificate listed only the names whose DNS records point at the gateway, but since 0.7.2 it also serves mail and autodiscover (and each tenant's sign-in name on a shared gateway). It now lists every name it serves (`configure.edge_served_names`), the same list the public certificate request uses.
- **Fixed: before public certificates, documents could not load.** With `ssl.enable=false` Collabora's file client reads its CA only from `storage.ssl.ca_file_path`, else OpenSSL's default trust, so our trust file was ignored and the deployment-CA certificate was refused ("unable to get local issuer certificate"). The office unit now sets `SSL_CERT_FILE=/opt/ou-tls/trust.crt` (deployment CA + Let's Encrypt roots); verification stays on; no image rebuild.
- Both apply to deployments configured from this release on.

### Fixed
- **mail/autodiscover showed a certificate error (ERR_CERT_COMMON_NAME_INVALID) until a public certificate existed, and always on LAN-only deployments.** Since 0.7.2 the gateway serves `mail.` and `autodiscover.` (proxied to the groupware VM), but its deployment-CA certificate listed only the names whose A record points at the gateway (`configure._tls` / `names_by_vm`), so the groupware's names were missing. The gateway's certificate of each scope (deployment and every tenant on a shared gateway) now covers every name it serves (`configure.edge_served_names`, also the source of `gateway.web_names`); on a shared multi-tenant gateway this also adds each tenant's `auth.` name, which was missing the same way. The groupware VM's own certificate is unchanged ([test_gateway_certs.py](ics/tests/test_gateway_certs.py)).
- **Documents stayed blank while the gateway served its deployment-CA certificate ("unable to get local issuer certificate", CheckFileInfo failed).** coolwsd's outbound WOPI client reads `ssl.ca_file_path` only when `ssl.enable=true` (Collabora Online cp-26.04.6-1 `wsd/wopi/StorageConnectionManager.cpp`; with `ssl.enable=false` only `storage.ssl.ca_file_path`), otherwise it trusts OpenSSL's default paths, which `net/Ssl.cpp` takes from `SSL_CERT_FILE` when set. The office unit now sets `SSL_CERT_FILE=/opt/ou-tls/trust.crt` (deployment CA + Let's Encrypt roots); verification stays on, no image rebuild ([test_deploy_configure_office_trust.py](ics/tests/test_deploy_configure_office_trust.py)).

Existing deployments need recreating (or the gateway's and the office VM's configuration re-run); no new agent or image.

## [0.9.1] - 2026-11-21

Both remaining user-facing failures, root-caused with the new Diagnostics logs on a live deployment:

- **Fixed: documents opened blank ("Unauthorized WOPI host").** Our Collabora build had no WOPI proof key (`Could not open proof RSA key ... /etc/coolwsd/proof_key`), so it signed no request, and OpenCloud's collaboration service refused every one ("ProofKeys verification failed: Invalid timestamp", CheckFileInfo 500). Each deployment now gets its own proof key (deployment secret `office-proof-key`, delivered read-only into the office trust volume), and the Office image **26.04.6-ou4** reads it from there. Neither the certificate trust changes of 0.8.1/0.8.2 nor disabling proof checks was the fix; both checks stay on.
- **Fixed: webmail answered HTTP 500 after sign-in.** The mailbox store (gromox exmdb) listened on `[::1]:5000` only, while webmail's backend dials `localhost`, which our Ubuntu image resolves to `127.0.0.1` only (`exmdb_client: HX_inet_connect to [localhost]:5000: Connection refused`, then `MAPIException` in grommunio-web). `cfg.gromox` now makes the store listen on both loopback addresses and allows both (agent **0.9.1-ou17**, golden image **version 13**).
- **Signing new images works again.** Since the artifact service became the signed identity, a new image could not be signed (the signer read only published images, and only signed images are published). The signer can read the bytes from the builder registry (`trust/source-registry`), still re-hashing them against the digest; the signed identity is unchanged.
- The functional audit uses OpenCloud Web 8's "New, Files Upload" path and does not wait for its notification stream.

New deployments get both fixes. Existing deployments need recreating (new agent, new Office image, new proof key).

- **Fixed: webmail answered HTTP 500 right after sign-in, for every user, on deployments from the Ubuntu golden image** (seen on officeunbound5, release 0.9.0). The mail store service (gromox exmdb, inside gromox-http) listened only on its default `[::1]:5000`. Webmail's backend (zcore) reaches it under the name `localhost` (gromox 3.13 `lib/exmdb_client2.cpp`: homeserver 0 becomes "localhost", port 5000 fixed) and resolves that through libHX as IPv6 with IPv4 mapping. The golden image's `/etc/hosts` lists `localhost` only as `127.0.0.1` (`blueprints/build/guest-image/customize.sh`), so the name became `::ffff:127.0.0.1`. Nothing listened there, so every mailbox open failed (`exmdb_client: HX_inet_connect to [localhost]:5000: Connection refused`, then `MAPIException` in `class.mapisession.php`). The lab VMs (Debian) map `localhost` to `::1` too, which is why the lab worked. `cfg.gromox` now sets `exmdb_listen=[::1]:5000 127.0.0.1:5000` in `gromox.cfg` and writes `exmdb_provider.cfg` with `exmdb_hosts_allow=::1 ::ffff:127.0.0.1`, so the store answers however `localhost` resolves and still accepts loopback only. Existing deployments need the new agent and a re-run of `cfg.gromox` ([test_guest_groupware.py](ics/tests/test_guest_groupware.py)).

### Fixed
- **Documents opened blank ("Unauthorized WOPI host").** Our source-built Collabora image had no WOPI proof key (`/etc/coolwsd/proof_key`; the distro package makes it in postinst), so coolwsd sent no `X-WOPI-Proof`/`X-WOPI-TimeStamp` headers and OpenCloud's collaboration service refused every WOPI call ("ProofKeys verification failed: Invalid timestamp"). The ICS now makes one RSA-2048 proof key per deployment (per tenant; deployment secret `office-proof-key`, vault-encrypted, wiped with the deployment) and writes it as `proof_key` (0600, owner 10001) into the office `tls` volume before the unit's first start; the audit records only its size. Office image **26.04.6-ou4**: `/etc/coolwsd/proof_key` is a symlink to `/opt/ou-tls/proof_key` (the rootfs is read-only; no key is baked into the image); the entrypoint refuses a file that is not a PEM RSA private key and warns when none is present. Proof verification in OpenCloud stays on. Needs the ou4 image built, dev-signed, published and pinned in `blueprints/catalog/components/office.yaml`; existing deployments need recreating.

Components: node agent **0.9.0-ou16**, portal **0.3.0-ou2**, webmail **ou-grommunio-web 5.2-ou4**, golden image **version 12** (first-boot attested and signed). The browser-based functional audit of a deployed stack (`blueprints/lab/tests/stack-functional/`) always verifies TLS.

- **New: the portal's admin area on deployments the ICS creates** (wiring; reads only for now). An administrator added under People (realm role `org-admin`) who signs in to the deployment's portal gets the admin area: overview, people, apps, groups and domain, read live from the deployment's directory.
  - **Settings → Network & domains → "Console public name"** (e.g. `console.example.com`; typed action `settings.network.update`). Deployed portals reach the ICS under `https://<that name>`. It must be a DNS name, never an address. Empty means deployed portals get no admin area.

The key is written to `/etc/ou-portal/ics-tenant-key` (0640), never to the environment file, and is removed when the admin area is switched off. ## [0.8.2] - 2026-11-21

- **Fixed: documents still opened blank on a deployment with public certificates.** The 0.8.1 fix covered Collabora; the remaining cause was OpenCloud.
  - OpenCloud and its collaboration (WOPI) service trusted only the deployment CA (`SSL_CERT_FILE`). The collaboration service reaches the Office server at `office.<domain>` through the gateway, which serves the Let's Encrypt certificate after `gateway.certificates.issue`, so it answered 500. The LDAP connection stays on the deployment CA alone ([test_deploy_configure_office_trust.py](ics/tests/test_deploy_configure_office_trust.py)).
  - Applies to deployments configured from this release on.

## [0.8.0] - 2026-11-20

First release of the 0.8 "Harbor" line: **people and administrators of a deployment are managed from the console, and the installation has a tenancy mode.**

- **New: People on every deployment page** (administrators). The list is read live from the deployment's directory: user, name, email, role (Administrator or User), Active or Locked. The deployment's own administrator (`ou-admin`) is marked.
  - **Add a person** with a role and a password (8 characters or more). An administrator gets administrator rights in files and the portal's organisation admin role, plus a mailbox. A user gets mail, files and documents.
  - **Change** a person's password, name or role. Changing the role removes the groups of the other role.
  - **Lock / Unlock**: the directory's password-policy lock. The password is kept; new sign-ins are refused while locked.
  - **Delete**: memberships are removed first. The deployment administrator and the last organisation administrator can't be deleted.
  - Every change is a typed action (`directory.account.set`, `.lock`, `.delete`) with approval and audit. Delete is high risk. Passwords exist only in the plan's encrypted secret and the signed agent request.
  - The directory is changed only through new agent runbooks on that deployment's identity VM (`cfg.ldap_list`, `cfg.ldap_groups`, `cfg.ldap_lock`, `cfg.ldap_delete`; closed schemas, no free-form LDAP). They are enabled only on identity VMs, so VMs from older images keep booting ([test_deploy_accounts.py](ics/tests/test_deploy_accounts.py), [test_agent_ldap_accounts.py](ics/tests/test_agent_ldap_accounts.py)).
- **New: installation tenancy mode** (System → "Tenancy mode"): single tenant (one organisation; the deploy wizard offers no multi-customer layout) or multi tenant (MSP: customers, each with a separate stack). It can be changed only while no deployment exists. Converting live deployments needs a migration plan that does not exist yet, so it is refused rather than half-done (typed action `settings.tenancy.set`, issue #32).
